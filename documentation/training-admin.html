Administrator course (v2.5.3)

This course is for people who administer Cronomicon, not just operate it: you set up scopes, decide who can do what, enrol runners, and hold the secrets. It assumes the operator course.

Audience: administrators About 45 minutes Operator course first

Take the operator course before this one. It covers the composable model, where definitions live, the Run dialog, blast radius, how runs start, and reading results. Everything below assumes all of it, and none of it is repeated here.

Two modules carry more weight than the rest. A2 and A4 are where an administrator's mistakes are expensive — one strands work where nothing can run it, the other locks people out or hands them everything. Slow down on both.

Two kinds of administrator appear throughout. A global administrator holds a role on every agency, looks after the installation, and works inside an agency by switching into it with the agency switcher under the wordmark. An agency administrator holds one on a single agency and manages what that agency owns: its scopes, its hosts, its secrets, its service accounts and its own agents. Where it matters, each module says which is meant.

A1 · Scopes, inventory and hosts

A scope is a named set of hosts. It is the closest thing to an Automate Schedule agent environment, and it does more than group machines: it is the boundary a run cannot cross. Getting scopes right is most of getting targeting right.

Scopes have a source too

Like jobs and schedules, a scope is either git or cronomicon. A git scope is defined in a repository and synced in; an Cronomicon scope is authored in the app. The same rule follows: if it came from Git, change it in Git.

Hosts work the same way, and this is where it gets interesting — a single scope can contain hosts from both sources at once. Hosts imported from a Git inventory carry a read-only badge; hosts you add in the app are yours to edit. When a name exists in both, the Cronomicon entry wins.

A scope belongs to one agency, and so does each host record

Every scope is in exactly one agency. A scope you create belongs to the agency you are working in — the one the agency switcher shows; the form names it and offers no other — and that agency's administrators manage it from then on. A scope that arrives from Git belongs to the agency whose repository holds its inventory: every agency syncs a repository of its own. Sync never moves one. Administration, the installation's administration (A2), has no repository and no scopes: a scope is always an ordinary agency's.

A scope does not move between agencies. Another agency gets the same hosts with Clone to an agency… on the scope's row: a new scope of its own. Changing a scope's agency is left to a global administrator, as a repair of a placement that was a mistake, and a scope from Git cannot be repaired at all. The scope's agency decides which runners may take its runs, so it is not a label (A2).

Host records and bastions follow the same rule. The ones you write by hand under Settings → SSH Targets belong to an agency, and only that agency's administrators change them; a host imported with a scope's inventory is simply its scope's. One placed in the wrong agency is a global administrator's repair: Edit, then Repair: move to another agency…, with a reason that is recorded.

Why the Cronomicon entry wins, and how to use that

Because it is the overlay. The repository describes the fleet as the team that owns the repository understands it; your overlay describes what is true for this Cronomicon installation — a different address, a bastion, a specific credential.

The practical use: you do not have to get a pull request merged to fix one host's connection details. Add the overlay, move on, and let the repository catch up. The practical risk: an overlay you forget about will keep winning long after the repository was fixed. Overlays are worth reviewing occasionally.

Ansible inventory

A scope can carry a full Ansible inventory in INI form. Cronomicon parses it into an advisory projection — groups, hosts, group variables — which is what the app shows you and what group targeting resolves against.

"Advisory" is doing real work in that sentence

Cronomicon parses a deliberately limited subset of inventory syntax. Anything it cannot parse it degrades loudly — it tells you, rather than quietly showing you an inventory that is missing half its groups.

The projection is for display and for resolving group targeting. The inventory that Ansible actually runs against is the one in the repository. When they disagree, the repository is right, and the projection warning is your signal that they do.

One hard rule: an inventory containing secrets is rejected outright. Not warned about — rejected. Inventories are read by more people than you think.

Which is it?

A host's SSH port is wrong for this installation only

An Cronomicon overlay host

Exactly what the overlay is for. Add the host in the app with the right port; it wins over the git-imported entry of the same name.

A new server everyone's automation needs to know about

Git

If it belongs to the fleet as everyone understands it, it belongs in the repository. An overlay here means the next person to read the inventory gets the wrong picture.

This scope's hosts sit behind a firewall the server cannot cross

An agent inside the firewall, bound to the scope — not a host-list change

Reachability is not a property of the host list. Which runners may take the work is settled by the scope's agency (A2, the next module); which of those runners actually reaches these hosts is the scope's runner binding (A3). Here the server cannot reach them, so the runner has to be an agent the scope's agency owns, sitting on the far side of the firewall.

A2 · Agencies and network isolation

An agency is a department's isolation zone. It answers two questions at once: whose is this? and which runners are allowed to execute this work? The answer to the second is enforced as a hard boundary, not a preference.

Two facts do most of the work:

A run carries its agency

Snapshotted when the run is enqueued, from the scope it is bound to. Repairing the scope into another agency later does not retroactively move runs already queued. A run with no scope carries its job's own agency.

A runner serves agencies

An agent serves exactly one: the agency that owns it, fixed by the registration token it enrolled with. Never self-declared by the agent — a runner cannot talk its way into an agency by claiming membership. The local runner, the server itself, serves the one agency a global administrator gives it, or none (A3).

The administration administers, the agencies run, and everything has exactly one

There is no such thing as "no agency". Every installation has one built-in agency, Administration (an installation made before 2.5.3 keeps its earlier name, Global or Central, until a global administrator renames it). It is the installation's administration, and it runs nothing. It holds the installation settings, the agency catalog, the installation's change log and Activity, the notices filed to it, the installation freeze, its alert rules (which match every agency's runs) with their push targets and contact, and the calendar catalogue (A6). It owns no scope, runner, registration token, schedule, script, job, workflow, reaction, secret, variable, SSH key, host record, bastion or repository connection.

Everything that runs belongs to an ordinary agency. Creating any of those things in Administration is refused, with this … would belong to the built-in administration agency, which runs nothing: switch to an agency, or name one, to create it there. A global administrator does that work by switching into the agency it belongs to.

And every scope, secret, variable, SSH key, host record, bastion and runner belongs to exactly one agency. Nothing new is shared between two departments by listing both. (A scope, secret, variable or SSH key that two departments shared before this rule existed keeps working as it was, and is listed under Notices until a global administrator settles it in one.)

Administration in the agency switcher

Global administrators, and readers of every agency, still find Administration in the switcher, after All agencies, as Administration. Working in Administration, the change log, Activity, Notices and Settings show the installation's. Its work pages — Jobs, Workflows, Scripts, Schedules (all but Calendars), the Scopes tab, Env Vars, Runners, SSH Targets, and the composer, publisher, schedule builder and workflow editor — show one line: Administration runs nothing. Switch to an agency to work.

With no default of their own, such a person starts in the one agency when there is exactly one, and on the All-agencies Dashboard when there are more. A default they store wins.

A new installation starts with Operations

At its first start, an installation with no agency but Administration gets one ordinary agency, named Operations. A solo administrator or a small team renames it and works there, and people are added with grants on it in Settings → Users & Access. A second agency later is an ordinary one, made under Scopes → Agencies, and nothing moves.

Until it is renamed, or a grant names it, its Dashboard shows global administrators a Name your agency card: a Name, and optionally the Administrators' AD group, which is granted the admin role on that agency. Dismiss hides the card in that browser.

Operations is made once. Delete it and it does not come back; with every agency deleted, the All-agencies Dashboard offers Create your first agency instead — a name, a repository now or later, and the same optional group. An upgrade that had only Administration gets Operations too, as the ready place for what Administration held.

The first administrator is set up as before, outside the app, and the administrator manual's first-run chapter describes it. Operations does not change that: a global administrator is anyone whose grant reaches every agency with the verb, not a member of an agency.

Giving something to another agency is a copy, not a move

Nothing moves between agencies. Another agency gets a scope by Clone to an agency… on the scope's row; a secret, a variable or a key by creating its own; and a job or workflow from a global administrator's Give to an agency…, which commits a copy into that agency's repository. The copy is the agency's from then on.

What remains of a move is a global administrator's repair, for a row placed in the wrong agency: Repair: move to another agency… on a secret, a variable or an SSH key, and on a host record or bastion under SSH Targets, with a reason that is recorded. It is refused when the target agency already owns something of that name — rather than leave two rows a job could not tell apart. Nothing is moved into Administration.

Scopes that were shared before this rule existed

An upgraded installation may hold scopes that sat in several agencies at once. They keep working exactly as they did. Nothing is moved for you, because which department a shared scope really belongs to is a decision, not something Cronomicon can work out.

Each one is listed in the Notices inbox as A scope in several agencies until a global administrator settles it in one. The same holds for a secret, a variable or an SSH key that two departments shared: it keeps resolving for both, and is listed as Shared by several agencies. Two more notices come from the upgrade alone: In no agency, for a row that ended up in none and that only a global administrator can re-home, and An agency was renamed by the upgrade, when a department was already called Global. A3 covers the inbox.

What agencies shared in other ways before 2.4.0 — a workflow whose jobs were several agencies', a reaction to another agency's definition, a job of Administration's repository on an agency's scope, a secret, script or schedule of Administration's that an agency's job used — stopped where it reached the other agency, and is listed in the inbox under the agency concerned. Nothing is copied for you: copy what each agency needs into it.

What Administration held at the 2.5.3 upgrade

Until 2.5.3 the built-in agency could run work of its own. From 2.5.3 it runs nothing, and the upgrade moves nothing for you. Whatever Administration owned stays where it is, does not run — a scheduled fire of it is skipped with the built-in administration agency runs nothing; move this definition to an agency — and is listed in one notice, The administration still holds work that no longer runs, one finding per kind, naming the rows and the way out:

  • secrets, variables and SSH keys — Repair: move to another agency… on Env Vars, with a reason;
  • scopes made in the app — the scope's agency, on Scopes (a repair, with a reason), or Clone to an agency… for each agency that needs the hosts;
  • host records and bastions written by hand — SSH Targets, Edit, then Repair: move to another agency…;
  • agents that serve Administration alone — deregister each and enrol it again with a token minted in its agency (A3);
  • jobs and workflows built in the app — their names are the installation's, so Administration's copy is noted, deleted and then deleted for good (Settings → Recycle Bin → Delete forever) before it is made again in the agency, or published into its repository;
  • schedules built in the app — made again in the agency, then deleted in Administration;
  • Administration's old repository connection — Settings → Repositories, working in Administration, Remove the leftover repository (a repair, with a reason); then connect the same URL and branch to the agency whose work it is, and its sync brings the definitions in as that agency's, except a job with no scope, which an agency's sync refuses: give each one of that agency's scopes first (cronomicon validate -agency lists them).

Working in Administration, each of those pages lists what is left under a banner that says it no longer runs, with only the actions that clear it. Every Dashboard tells global administrators Administration still holds … which stopped running in 2.5.3. Review them → until it holds nothing. An upgrade that had no agency but Administration gets Operations, the ready place to move it to.

Two environment settings went with Administration's work. The CRONOMICON_GITLAB_* settings, which configured Administration's repository, are ignored. CRONOMICON_RUNNER_BOOTSTRAP_TOKEN is refused: an agent enrols with a registration token minted in its agency. Either, still set, raises Environment settings that no longer apply are set and a warning at start.

The dispatch rule, exactly

It has no fallback in either direction, and the second half is the one people miss:

  1. A run is claimed only by a runner that serves the run's agency. A Finance run goes to a runner that serves Finance, and to no other.
  2. A run of a job with no scope (one made before 2.5.3: every job names a scope now) belongs to the job's own agency, and is claimed only by a runner that serves that agency. It is not picked up by whichever department's runner happens to be idle.

So there is no pool that every runner drains, and a department's agent is not spare capacity for anyone else. This is deliberate: an isolation boundary that leaks in one direction is not an isolation boundary. Administration takes no part: a definition Administration still holds is refused when it would start, rather than queued for a runner that would never come.

The agency is the first of several conditions a runner must meet before it takes a run; A3 lists the rest. It is the one that nothing else can widen.

Check yourself

Scenario A1

The Finance agency has one agent, and it is doing Finance's work happily. A new isolated network that belongs to the Tax agency needs automation, and you would like the Finance agent to take Tax's runs as well.

How do you make that happen?

Add Tax to the agent on its Runners row, so that it serves both

No, and the row offers nothing to do it with. An agent has no list to edit: it serves exactly the agency that owns it. One agent holding two departments' keys and reaching two departments' networks is precisely what an agency exists to prevent. Two agents on one machine are a different thing: each runs as its own OS user and holds only its own agency's keys.

You do not. A second agent is enrolled, with a registration token minted for Tax

Correct. There are no shared agents. The token decides the owner, and the owner is what the agent serves. Tax's own administrators can mint that token and enrol that agent; it does not take a global administrator.

An agent is a small binary. One per agency is the intended shape, not a limitation. It need not be a machine each: a second agent runs beside the first on the same host, under an OS user, a unit and directories of its own, when the install command is given an Instance name (--instance; the runner install guide has the procedure). A container runs one agent, so two agencies there are two containers.

The local runner, the server itself, is no help here either: it serves the one agency it was given, it runs shell jobs only, and the server cannot reach an isolated network.

Have the agent register again and declare both agencies

No. An agent never declares what it serves. If it could, any machine holding the agent binary could enrol itself into the department of its choice. The registration token carries the agency, and a token carries exactly one.

Takeaway: an agent serves exactly the agency that owns it. Plan runner coverage per agency: every agency whose work needs an agent needs one of its own.

Scenario A2

A job bound to a dmz scope has been queued for twenty minutes. The dmz agency's only agent shows as offline.

Can you get the run moving by pointing the job at a scope in another agency, one whose runner is up?

Yes — re-binding the job releases the queued run to the other agency's runner

No. The run snapshotted its agency when it was enqueued, so the run that is already waiting keeps waiting. Editing the definition changes what happens next time.

No — and you should not want to. Fix the runner.

Correct on both counts. The queued run keeps the agency it was enqueued with, a job may name only its own agency's scopes in any case, and the boundary exists because those hosts are isolated for a reason. Routing round it is precisely the thing agencies prevent.

The right move is to bring the agent back. An offline agent re-admits itself automatically on its next successful poll, so often the answer is fixing the network or the service on that host and waiting.

Yes, after cancelling and re-triggering the run

It does not get that far: a job runs on its own agency's scopes only, so a run against another agency's scope is refused. And whatever such a run did, it would not be the dmz work — the other agency's runner cannot reach the dmz hosts anyway. If you find yourself here, the question to escalate is whether the scope's agency is right, not how to bypass it.

Takeaway: a run's agency is fixed at enqueue. Agencies are an isolation guarantee — when one blocks you, that is the feature.

A3 · Runners

A runner is what takes a run and carries it out. There is one way a run happens: it is queued, and a runner claims it. Runners come in two kinds.

An agent

A small external binary, cronomicon-runner, installed on a machine and polling Cronomicon for work — usually inside the network its targets sit in. It runs whatever it has the tools for, Ansible included, and can watch for arriving files. It serves exactly the agency that owns it.

The local runner

The Cronomicon server itself, running shell jobs over SSH from where it sits. It is one row in the Runners view, marked this server. There is exactly one, and it cannot be deregistered. It runs bash, perl, powershell and python, nothing else, and serves one agency, chosen by a global administrator, or none, and is then off.

You need an agent when the work is any agency's but the local runner's, when the server cannot reach the targets directly, when the work is Ansible, when a job binds an SSH key, or when a job watches for arriving files.

Nobody chooses a runner. No field on a job, a script or a run says where it executes, and the Run dialog offers nothing to pick. Where a scope's jobs run is decided in one place only — the scope's runner binding, further down this module.

Who takes a run

The first runner that asks takes a queued run — provided it is eligible. Every one of these must hold:

  1. Agency. The runner serves the agency of the run's scope. A run with no scope is its job's agency's.
  2. Scope binding. If the scope is bound to runners, the runner is one of them. The local runner can be bound like any other.
  3. Capability. The runner can run the run type and satisfies the job's requires. The local runner runs only the shell types and satisfies no requires at all; Ansible needs an agent with the toolchain.
  4. Secret injection. A run that injects secrets needs a runner allowed to receive them: an agent you have flagged, or the local runner, which resolves the references itself on the server.
  5. SSH key bindings. A run that binds an SSH key — declared on the job, or added in the Run dialog — is never taken by the local runner. A bound key is delivered as a file on the machine that runs the job, and only an agent does that.

Read the consequence slowly, because it is the one that surprises people after an upgrade. In the local runner's agency, where an agent and the local runner can both serve, and a scope is not bound, a shell job may be taken by either, and not always the same one. A job that used to run from the server may now be taken by an agent; one that used to run on an agent may now be taken by the server. If that matters for a scope, bind it. That is the only control.

What a run does when no runner is eligible

It waits, and History says why, in a sentence that names the unmet condition: no online runner serves Finance, no online runner can run ansible jobs, the local runner would take this run and is not running, and so on. Your operators are taught to read that sentence and bring it to you.

One case is refused rather than left waiting. A shell job that binds an SSH key, on a scope that no registered agent serves, can never start — so a manual run or an API trigger is refused with key_binding_requires_runner, a scheduled fire leaves a skipped row, and a workflow step fails. An agent that is merely offline is an ordinary wait.

The local runner

Turning it on, and what you are agreeing to

The local runner lives under Settings → Local runner, which only a global administrator sees. Three things are set there: its Agency, its State (on or off) and its Runs at once.

On a new installation it is Unassigned (off), and its State reads Off: it belongs to no agency. Turn on… waits until it has an agency. Turn it on and the server itself holds SSH private keys in memory and opens outbound SSH connections to job targets, and it writes a loud warning to its log each time it starts claiming. That is a real change to what the server is, which is why it is a decision and not a default.

It starts claiming at once: its agency's queued shell runs, which no other runner has taken, run from the server. Turn it off again and the runs it is carrying finish, it claims nothing more, and nothing is failed — but a scope bound only to it stays closed until it is back.

What it serves: one agency, or none

An agent serves its owner and nothing else, and so does the local runner. Since 2.5.3 its owner is the one ordinary agency a global administrator picks under Agency, and it takes that agency's runs as an agent of it would. It is never Administration's to run: Administration runs nothing.

Changing its agency is refused while it is running a run, and while scopes are bound to it — their agency unbinds them first. The change clears its host-key approvals, so the new agency's administrators approve the keys of their own hosts, and it turns the local runner off: turn it on again once those keys are approved. The change is recorded for the installation and for both agencies.

At the 2.5.3 upgrade it became unassigned and off, because until then it served the built-in agency, which runs nothing now. If it was on, the Notices inbox lists The local runner belongs to no agency and is off until it is given an agency.

Keeping the server out of it altogether

Leave the local runner off or unassigned, or go further and start the server with CRONOMICON_LOCAL_RUNNER=forbid. That forces it off and locks the setting, whatever its agency: the State reads Forbidden on this host and nobody can turn it on from the app.

If the local runner is the only runner that could take a run and it is off or forbidden, the run stays queued and History says exactly that. An agency whose shell jobs have nowhere to run is also listed in the Notices inbox.

An agent has an owner

An agent's owner is the agency whose administrators manage it. What it serves is the agency whose runs it claims. For an agent those are one and the same fact, and it is fixed when the agent enrols.

Enrolling one — and who can

On the Runners view, + Add Runner mints a single-use registration token and builds the one line to paste on the host. The token is minted for an agency — the one you are working in — and that agency becomes the agent's owner, so switch into the department the agent is for first: an agent cannot be handed to another agency afterwards, and the way back is to deregister it and enrol it again. Working in Administration, the mint is refused (Administration runs nothing: mint the token working in the agency the runner is for). The token is good for 24 hours and for one enrolment.

An agency's administrators mint tokens for their own agency and manage the agents it owns: settings, tags, host keys, deregistering. They cannot touch another agency's. Nobody mints a token for Administration, and one minted for it before 2.5.3 is refused at enrolment, as is the retired CRONOMICON_RUNNER_BOOTSTRAP_TOKEN.

A department with no machine of its own is still served by an agent it owns: a global administrator deploys one for it, on whatever host is available. There are no shared agents.

Legacy placements — agents that served several agencies before

An upgraded installation may have agents that served several agencies. Each is now a legacy placement: it is owned by Administration, so only a global administrator manages it, and it can be narrowed and never widened. Since 2.4.0 it took only the built-in agency's work, and since 2.5.3, when Administration runs nothing, it takes none: the runs of the agencies on its list wait for agents of their own. Its row carries a Legacy placement mark and it is listed in the Notices inbox.

Settle one in this order:

  1. Enrol an agent for each agency the old runner serves.
  2. Re-bind each of that agency's scopes that is bound to the old runner to the new agent, scope by scope.
  3. Copy the approved host keys for that agency's hosts to the new agent — Copy from a runner… under its Trusted host keys.
  4. Only then take the agency off the old runner, or deregister it.

Taking an agency off cannot be undone, which is why it comes last. When the old runner is down to a single agency, Hand to that agency makes it the owner and the notice clears.

Three states, and one of them is not stored

Online

Heartbeating normally. Claiming work.

Degraded

Has not heartbeated for more than two minutes. Still counts as reachable.

Offline

Gone long enough to be treated as absent. Re-admits itself on its next successful poll.

Degraded is computed when you look, never written down

It is derived from the last heartbeat at read time. There is no background job flipping runners to degraded and no stored value to go stale — which means the state you see is always current, and a runner that recovers stops being degraded the instant it heartbeats.

Recovery actions are available on degraded runners, not just online ones. A runner that has gone quiet is exactly the one you want to be able to act on.

These states are an agent's. The local runner does not heartbeat from anywhere — it is the server — so its row reads offline for one reason only: it is turned off (unassigned, it is always off), or forbidden on the host. Expand the row and it says which. It is never removed for being quiet.

Capabilities are flags you set, not claims the agent makes

An agent does only what it was started and configured to do. Two capabilities matter most, and both are opt-in:

Checkout — running full Ansible playbook projects

Off unless the agent was started to allow it, and then bounded: a repository allowlist, a server-pinned commit, a read-only deploy credential, and a secret scan of the tree before it runs. Body-only runs need none of this.

File watching — another reason to deploy an agent

Also opt-in, with an allowlist of paths it may watch. The agent reports what it observed; the server decides whether that means a run. The agent never triggers anything itself.

It polls rather than using filesystem notifications — deliberately. The stability check ("size unchanged for N seconds") needs polling anyway, and filesystem notifications do not fire for writes made by another host over NFS or SMB, which is exactly where drop directories live. A watcher that silently never fires there would be worse than a slower one that always works.

Secret injection — a flag with teeth

A job that binds secret references may only be claimed by an agent you have flagged for secret injection. An unflagged agent leaves such a run queued for an eligible runner rather than claiming it and failing. The local runner needs no flag: it is the server, which holds the secret store, and resolves the references without their leaving the process.

Same shape as agency isolation: eligibility filters dispatch, so the wrong runner never sees the work.

Scope binding — naming the runners that reach a scope's hosts

An agency says which runners may take a run; among those, every eligible runner is interchangeable. When only some of them should take a scope's runs — because only they reach its hosts, or because the work must stay off the server — you bind the scope to those runners: Scopes, expand the scope, Runners, Bind runners…. From then on only the bound runners claim that scope's runs, on every path: manual, scheduled, workflow step, reaction, file arrival. The binding narrows on top of the agency rule; it never widens it.

This is the only way to say where a scope's jobs run. Bind the agent that reaches the hosts to keep a scope's shell jobs off the server; bind the local runner to keep them on it. A run on a bound scope uses the bound runner's keys and the host keys approved for that runner. And the binding does not make a runner able: a scope bound only to the local runner cannot run Ansible, or a job that binds an SSH key.

Binding takes authority over the scope, and a runner that serves the scope's agency. It does not take authority over the runner.

A binding outlives its runner. Deregister a bound runner and the scope stays bound to it: its runs wait, and each one says why. That is deliberate — the alternative is a confined scope quietly reopening to its whole agency. You replace the runner, or restore its placement when the host enrols again.

Runner tags play no part in this. They are labels for finding runners; nothing is dispatched on one. Before 2.2.0 a job could be pinned to a runner tag — that pin is gone, and a runner_tag line left in a Git job file is ignored with a warning. An executor line gets the same treatment (A6).

Host keys — what a runner trusts, and who said so

A runner connects only to a host whose SSH key someone has approved for that runner. That holds for the local runner exactly as for an agent, and nothing is trusted on first contact: no runner captures a key the first time it sees a host. You approve keys from the Runners view — expand the runner, Trusted host keys, then Scan keys… to have the runner scan a whole scope or a list of hosts from where it sits, Paste keys… to supply lines yourself, or Copy from a runner… to carry what another runner trusts. Every route ends on the same screen: each fingerprint, computed by the server, shown for review before anything is trusted.

The review is the control. Compare each fingerprint with the host's own. A key that differs from one already trusted is marked Changed and is never ticked by select-all; approving it replaces the old key instead of leaving both trusted. A host behind a bastion cannot be scanned, so its key is pasted; the bastion itself is scanned, and is verified like any other host, under its own address.

Every approval, rejection and removal is recorded with the runner, the person and the source. For an agent, approved keys are delivered to its own known_hosts file, and the agent reports what that file really holds — so a key somebody put there by hand shows up as not approved here instead of staying invisible. For the local runner there is no file: the record of approvals is what the server trusts, an approval is in force at once, and its keys are for the administrators of its agency to decide, as an agent's are its owner's.

What it looks like when a key is missing: a run fails for that host with host_key_unverified, and the message says where to approve one. Test connection on Settings → SSH Targets answers no approved key rather than quietly capturing the key it was shown — and there is no longer a pin to clear there; replacing or removing a key is done in the runner's Host keys dialog. The Notices inbox lists, scope by scope, the hosts the local runner takes runs for and has no approved key for.

One limit to know: the local runner holds one key per address and key type. Two different machines that share an address behind two different bastions cannot both be trusted by it.

Protocol version, and why an old runner is refused rather than half-served

Agent and server share a wire protocol version, and the server accepts only the current one. An agent that is behind is refused on its next poll, with an error naming the version it needs, rather than being handed work whose newer fields it would silently drop. A dry run that applies for real is the failure this prevents.

So a server upgrade that moves the protocol is a fleet upgrade. 2.2.0 moved it to 14: every agent is upgraded with the server. A refused agent keeps its row and its identity, and Copy upgrade command on its row is the fix.

The house rule for buttons still holds across the whole app: a precondition disables with a tooltip naming the fix; only irrelevance hides. A missing button is a mystery; a disabled one that says why is an instruction.

The Notices inbox

The top bar carries a Notices button with a count. It opens an inbox of conditions that hold right now and need a person — not a log of things that happened. Three properties follow from that, and they are worth having straight before you open it:

  1. A notice clears itself when its cause is put right. You do not mark it done.
  2. Dismiss hides, it does not fix. It is for a notice you have read and are leaving as it is, and it records who dismissed it. If the condition goes away and comes back, so does the notice.
  3. You see your own agencies' notices. They are grouped by agency, and shown to that agency's administrators; the button's count is for the agency you are working in. The install-wide ones are filed under Administration and are a global administrator's.

Each notice names the place its remedy is made. What you will find there, by what it is about:

Where shell jobs run
  • Shell jobs that ran from the server may now run on an agent, …that ran on agents may now run from the server, and …that ran in two places may now run in either — the upgrade recorded where each unbound scope's shell jobs used to run, and both kinds of runner can now take them. The two are not the same place to run: different keys, different approved host keys, and a run where only some hosts fail ends as a warning on the server and as a failure on an agent. Bind the scope to the runners that should serve it and the notice clears. If either is fine, dismiss it.
  • The local runner belongs to no agency and is off — it was on before the 2.5.3 upgrade, which left it unassigned. A global administrator gives it the agency whose shell jobs it is to run, under Settings → Local runner, and the notice clears; it stays off until that agency has approved its hosts' keys and a global administrator turns it on.
  • An agency's shell jobs have no runner — no runner that serves it can run a shell job. Enrol an agent for the agency, or ask a global administrator to give it the local runner.
  • A shell job requires what no agent has — a job's requires is read for shell jobs too, and the local runner satisfies none. Enrol an agent that has it, or drop the requirement.
Lines left in Git that no longer do anything
  • Jobs in Git still declare an executor, which is ignored — one notice per agency, naming the jobs. Remove the executor line from each job's file, or from its script's sidecar when the job took it from there. It clears at the next sync.
  • A runner-tag pin that could not be converted — a job was pinned to a runner tag before scopes could be bound and the pin had no binding to become, or its Git file still says runner_tag and its scope is not bound. The notice gives the reason. Bind the scope to its runners; for a leftover line, removing it will do as well.
Ownership that needs settling
  • The administration still holds work that no longer runs — filed under Administration, one finding per kind, each linked to the page its way out is made on, working in Administration (A2 lists them). It clears kind by kind as Administration stops holding each.
  • A job binds a secret, variable or key only Administration has, A host only Administration has a record for, A job is built on a script of Administration's repository and A job or workflow is bound to a schedule of Administration's — filed under the agency whose definitions depend on what Administration holds, so that its administrators know why its runs fail. Each clears as the row leaves Administration.
  • A scope in several agencies — a global administrator settles it in one agency, as a repair.
  • A runner that serves agencies it is not owned by — a legacy placement. Narrow it, or replace it with agents each agency owns, in the order given earlier in this module.
  • A job's target host is not in its scope — fix the job, or add the host to the scope.
  • A host record or bastion names a key its owner cannot use — pick a key of the record's own agency.
  • A Vault path outside its agency's prefixes — add the prefix to the agency, or correct the path (A5).
Host keys for the local runner
  • The local runner has no approved key for some hosts — it takes a scope's runs and would fail on those hosts. Approve their keys under Runners, on the local runner's row, in Trusted host keys.
  • Two records for one address had different host keys — raised by the upgrade, which carried the keys the server already held into the local runner's approved keys and could keep only one per address. If it is one machine whose key changed, scan it and approve the current key. If it is two machines sharing an address behind different bastions, the server can serve only one of them: run the other's scope on an agent inside that network.
Calendars from Administration, and settings that no longer apply
  • A calendar from Administration has an update — the catalogue calendar an agency's copy came from has changed, and the copy asks before updating. Its calendar editors press Update on Schedules → Calendars (A6). When the agency's own bindings forbid the update, the notice says why.
  • A calendar from Administration is no longer offered — the catalogue calendar was deleted. The copy stays, read-only, until the agency makes it its own or deletes it.
  • Environment settings that no longer apply are set — filed under Administration: a CRONOMICON_GITLAB_* setting, or CRONOMICON_RUNNER_BOOTSTRAP_TOKEN, is still set on the server. Since 2.5.3 the first are ignored and the token is refused. Remove them from the server's environment.

A4 · Who can do what

This is the module to read twice. Access mistakes are quiet: nobody reports being able to do something they should not.

Two halves, and they must come from the same grant

Access is not "a role" plus "some scopes" held separately. It is a grant: an AD group, a role, and where that role applies — one row, one package.

The rule that follows is the single most important thing here: a permission and the agency it applies to must come from the same grant. Cronomicon never combines the verb from one grant with the territory of another.

The seven permissions

  1. Trigger jobs — start a run.
  2. Kill jobs — stop, pause and resume.
  3. Manage variables & secrets — variables, secrets and their bindings.
  4. Publish to the repository — push definitions to the agency's repository.
  5. Configure application — on an agency: its scopes, its repository, its host records, its alerts and its agents. On every agency: the installation's settings as well.
  6. Manage roles & access — roles and grants. The one that can grant itself away.
  7. Create jobs & workflows — author jobs and workflows in the app, within the agencies the grant reaches.

Four roles come built in — admin (all seven), approver (trigger, kill, publish), operator (trigger, kill) and viewer (none, read-only) — and a global administrator can define more from the same seven.

Where a grant applies

All scopes

Unrestricted: every agency, Administration included, and anything created tomorrow. Whoever holds a permission this way is a global administrator for it.

One agency

The role applies to what that agency owns — its scopes and everything bound to them.

No grant

Zero access. Not "everything": such a person sees nothing and can change nothing.

That third one is the trap: an empty grant does not mean unrestricted. It fails closed. Some schedulers treat an empty restriction list as "no restriction"; Cronomicon does not, and nothing you have carried over from such a tool should assume it.

A grant names one agency or all of them. It never names Administration on its own: what Administration keeps is changed only by someone whose grant covers every agency. That is also why a team cannot share Administration as a workplace, and why a new installation comes with Operations (A2): people are given grants on an ordinary agency.

Global administrators and agency administrators

Those two shapes of grant give two kinds of administrator, and the second kind is meant to be self-sufficient. A department should not need to raise a ticket with the people who run the installation to do its own housekeeping.

An agency administrator

Manages what the agency owns: creates scopes in it, keeps its repository connection, its host records and bastions and its alert rules, writes its secrets — Vault-backed ones inside the agency's Vault paths — mints its service accounts, grants its own people access, and enrols and manages its own agents.

A global administrator

Changes the installation and what Administration keeps: the Installation settings, the agency catalog, each agency's Vault paths and directory groups, the role definitions, the local runner and its agency, Administration's alert rules and the calendar catalogue. Administration runs nothing, so to work — a job, a scope, a secret, an agent — they switch into the agency it belongs to.

The four rules an agency administrator grants access under

An agency administrator who holds Manage roles & access can grant and revoke access for their own agency, and mint its service accounts, under four rules:

  • Own agencies only. A grant on another department is not theirs to write.
  • Never all scopes. Only a global administrator hands out an unrestricted grant.
  • No amplification. They cannot grant a permission they do not themselves hold on that agency.
  • Listed groups only. A grant names a directory group that a global administrator has listed for the agency (Scopes → Agencies, the agency's panel, Edit groups). The list starts empty.

The role definitions themselves are shared by every agency, so editing one is a global administrator's job.

Settings shows each of them a different page

Settings is in two groups. Agency holds what an agency's administrators change for themselves: Users & Access, Service Accounts, Repositories, SSH Targets, Alerts, Audit Export (an agency administrator's own; a global administrator has Audit & Compliance) and the Recycle Bin. Installation holds what only a global administrator changes: General, Notifications (the mail relay; each agency's alerts are under Alerts), Vault, Observability, Log Storage, Audit & Compliance and Local runner.

The Installation group is not greyed out for an agency administrator — it is not there. A whole section that can never apply to its reader is irrelevance, and irrelevance hides. So when you write instructions for a department, do not send them to an Installation section; they will land somewhere else. Each section has its own address, which makes linking to the right one easy.

The Recycle Bin is the odd one in the Agency group: it is not an administrator's at all, but anyone's who creates jobs and workflows in the agency.

Working in Administration, Settings shows the installation's. Repositories there holds only the Allowed hosts card — Administration has no repository — and, on an upgraded installation that still has one, Administration's old connection with Remove the leftover repository. Working in an agency, Repositories shows that agency's repository, or the card to connect one.

One more thing that catches people: AD group names are case-sensitive. Finance-Ops and finance-ops are different groups, and a grant against the wrong case simply never matches — silently, because there is nothing to report.

Check yourself

Scenario A3

Dana is in two AD groups. One grants viewer across all scopes. The other grants operator on the Finance agency.

Can Dana run a job in the Tax agency?

Yes — she has operator somewhere, and viewer everywhere

No, and this is exactly the mistake the same-grant rule exists to prevent. It takes the verb from the second grant and the territory from the first. Cronomicon never does that.

No. She can see Tax jobs, and run nothing there.

Correct. Each grant is evaluated whole. The viewer grant reaches Tax but carries no verbs; the operator grant carries the verb but does not reach Tax. Neither grant answers yes on its own, so the answer is no.

She can run jobs in Finance, and read everywhere.

No, and she cannot see Tax jobs either

Half right. The viewer grant does reach all scopes, so she can see Tax jobs — she just holds no verbs to use on them. Visibility and capability are separate questions, answered by different grants.

Takeaway: evaluate one grant at a time, whole. "Can do this somewhere" is never "can do it here".

Scenario A4

A contractor needs to run one specific job in Finance and nothing else. You are looking for a per-job permission and cannot find one.

What is the right shape?

Grant operator on all scopes and rely on them only touching that job

No. That is not access control, it is a request. It also fails the question anyone will ask afterwards: what could this account have done?

A scope containing only what that job targets, an agency for it, and a grant against that

Correct. There is deliberately no per-job permission — a grant names an agency, and reaches the scopes that agency owns. Narrowing access means narrowing the territory, which also narrows the blast radius of anything that goes wrong.

Count what the new agency needs before you promise a date, because an agency is a real zone and not a label. A global administrator creates it, together with its repository. It needs a runner that serves it — an agent enrolled for it, or the local runner if a global administrator gives it to this agency rather than another — or the contractor's run will wait for ever. The job itself has to be the new agency's: a copy in its repository, which Give to an agency… makes. And the secrets and keys the job binds must be the new agency's own; Finance's are not usable from it, and Administration holds none.

If that feels like a lot of structure for one contractor, that is the system telling you something true: one job's worth of access is unusual, and it is worth being deliberate about.

Make a custom role holding only "trigger jobs" and grant it everywhere

Better than the first option, and still wrong on the territory: "everywhere" means every scope including ones that do not exist yet. The custom role is a good instinct — pair it with a narrow agency rather than all scopes.

Takeaway: the unit of access is the agency and the scopes it owns. Narrow the territory, not the job list.

Scenario A5

Tidying up the role definitions, you open the built-in admin role and untick Manage roles & access.

What happens?

Cronomicon refuses — the admin role cannot give that permission up

Correct. There is a guard for exactly this, because the failure is unrecoverable from inside the app: the permission you would be removing is the one that reaches this screen, so nobody left could put it back. The box is locked on the admin role, and the server refuses the change whatever the screen does. The same guard stops you clearing it from the last role of any name that still holds it.

It is the one place where the system overrules an administrator, and it earns it.

Know where the guard stops, though. It protects the role. It does not count grants: revoke the last grant that gives anybody the admin role on all scopes and Cronomicon lets you. The way back from that is outside the app — the administrator manual's first-run chapter describes it — so read a grant twice before you delete it.

It succeeds, and you fix it by editing the database

It does not succeed. And "fix it in the database" is a bad plan you should not need — which is why the guard exists.

It succeeds, and everyone is silently promoted to admin

No. Cronomicon fails closed everywhere — the failure mode of losing access control is that nobody can do anything, never that everybody can.

Takeaway: the system fails closed, and guards the one door that cannot be reopened from inside.

Two operational notes

A change to roles or grants is in force at once. Within seconds, on the person's very next click — nobody is signed out, and nobody has to sign in again to pick it up. That cuts both ways: a grant you revoke stops working while its holder is mid-task, so say it out loud before you make a change during business hours.

There is one change Cronomicon cannot see: someone removed from a group at your identity provider keeps that group until they next sign in. For that, a global administrator has Sign out everyone else… on the menu under their own name. And upgrading from a release before this behaviour signs everyone out once, on its own.

Ask a confused user to open My access. It is on the menu under their name at the foot of the sidebar, and it shows what Cronomicon actually resolved for them: each grant that reaches them, with its role, the agency it is on, what it permits and the group it came through — and, separately, the groups of theirs that no grant names. That last list is where a mis-cased group name shows up, which is the usual answer to "I was added to the group and nothing changed".

A5 · Secrets, variables and credentials

Four different things live near each other. Choosing the wrong one is how values end up in logs.

Env var

An ordinary value. Visible in logs. For configuration, not credentials.

Secret

Encrypted at rest, injected only into runs that declare it, masked in logs as it is written.

Vault reference

Same, but the value lives in Vault and is fetched at dispatch. Cronomicon stores the name.

SSH credential

A first-class key for connecting to hosts, with its own rotation and usage tracking.

Each one belongs to an agency

A secret, a variable and an SSH key each belong to exactly one agency — the one you are working in when you create it — and that agency's administrators manage it. Only that agency's runs use it. Administration holds none: creating one there is refused, and one it held before 2.5.3 resolves for no run until it is moved to an agency (A2).

Nothing is handed to another department. An agency that needs the same value creates its own row. For a secret two agencies need, a global administrator can give both the same Vault prefix, and each keeps its own row naming the same Vault path. Moving a row between agencies is a global administrator's repair, Repair: move to another agency… on the row, for one placed in the wrong agency.

The consequence for a run: a job resolves a reference from its own agency only. A run with no scope belongs to its job's agency and resolves that agency's rows, so a job that binds a row of another agency's, or of Administration's, is refused.

Vault paths are divided between agencies

The installation has one Vault connection, and a global administrator divides it. Each agency has a list of Vault paths — path prefixes, on its row under Scopes → Agencies — and the agency's administrators may name any path inside one of them for the secrets and keys the agency owns. An agency with no prefix cannot create a Vault-backed secret or key; any it already owns keep working, and cannot be edited until a path that covers them is assigned. Administration has no list, because it holds no secrets or keys: a global administrator who needs a Vault-backed one creates it in the agency, inside that agency's prefixes, like anyone else.

The rule is applied when a reference is written and when a row is moved — a path outside the agency's prefixes is refused there and then. It is never applied at run time: a job does not start failing because somebody edited a prefix list. What already falls outside is listed in the Notices inbox instead, as A Vault path outside its agency's prefixes, until you add the prefix or correct the path.

A prefix covers whole path segments, and case matters. secret/data/tax covers secret/data/tax/db; it does not cover secret/data/tax-audit/db.

An SSH key does two different jobs — and only one of them works on the local runner

Connecting as it. A host record, a job or a single run can name the key a runner logs in with. That works on every runner, the local runner included.

Binding it. A job can also bind a key as a reference, so that the script gets the key as a file on the machine that runs it. Only an agent can do that. The local runner never takes a run that binds a key: such a run waits for an agent that serves its scope, and when no registered agent does, it is refused — key_binding_requires_runner — rather than queued for a runner that does not exist.

So before a department binds a key on a shell job, it needs an agent of its own. If all it wanted was to log in with the department's key, that is Connect as, and needs none.

Jobs bind names, never values

A job declares which secrets it needs by reference. Nothing sensitive is stored in the job definition, which is what makes it safe for that definition to live in Git and be read by anyone with repository access.

At dispatch, only the declared references are resolved, injected into that one run, recorded in an audit row, and fed to the log redactor. A run that does not declare a secret cannot see it.

Redaction happens on the way in, not on the way out

Values are masked as the log is written, so there is no unredacted copy on disk to leak later.

The corollary matters for your operators: ordinary variables and run inputs are not masked, deliberately, because they are usually what someone needs to see when diagnosing. So the rule to teach is simple — if a value must never appear in a log, it must be a secret, not a variable.

Run-as credentials belong to the agency, not the job

One job body can run under each department's own credential: the credential is resolved per run from the run's agency, rather than baked into the job. That is what lets the same job, copied into each department's repository, run under each department's credential without any of them holding another's.

A become password is never an environment variable. It has its own path precisely so it cannot land in an env dump.

The one that will catch you in a fresh install

The secret store needs its encryption key configured. Without it, creating a secret fails — and the failure is at save time, not at startup, so a server that looks healthy can be unable to store a secret.

Check it as part of standing an environment up, not when somebody first tries to add a password.

A6 · Authoring in the app

Most definitions come from Git. Cronomicon can also author its own, and knowing which surfaces do that — and which deliberately do not — saves a lot of hunting.

What you can author in the app
  • Compose — build a job by binding a script to a scope, schedules, variables and declared run inputs. There is no field for where the job runs: the composer shows a one-line Runs on note, worked out from the run type and from whether the job binds an SSH key, and that is all. Its Calendars (optional) field names the job's own Forbid and Allow calendars.
  • Workflow Editor — compose a workflow from job steps, with a visual canvas, and the same Calendars (optional) field.
  • Schedule Builder — author schedules, with a cron helper.
  • Calendars and Reactions — both authored in the app.
  • Scopes, agencies, runners, secrets, grants — all app-owned.

All of the authoring surfaces are permission-gated. Tags and notes are the deliberate exception: any signed-in user can add those to anything.

All of it is done working in an agency. Working in Administration, the composer, publisher, schedule builder and workflow editor say Administration runs nothing. Switch to an agency to work. The one authoring surface Administration keeps is its calendar catalogue.

Calendars: Administration's catalogue, and each agency's copies

Calendars are app data, never files in a repository. Each agency has its own, made by its calendar editors (anyone who may create jobs and workflows there). A calendar marked freeze — Freeze: forbid its days to every start of the agency, in its editor — stops every start of that agency on its days, a person's Run included, whether or not a job names it; other agencies are untouched. In a YAML or JSON file the key is still global.

The catalogue. Working in Administration, Schedules → Calendars is the installation's catalogue: global administrators create, edit and delete calendars there, and no run reads them. An agency takes a copy: its calendar editors use Add from Administration (a catalogue calendar, the name it goes by here, and When Administration changes it), or a global administrator uses Add to agencies… on the catalogue row. The row says how many agencies have it and how many are behind, as in 2 agencies · 1 behind.

A copy is the agency's own calendar, listed under From Administration apart from Our calendars. It is read-only there — its days, description and flags change only by an update — and can be deleted. Make it our own turns it into an ordinary calendar of the agency, editable, with no more updates. If the catalogue calendar is deleted, its copies stay, marked no longer offered, read-only until made their own.

Updates. A change in the catalogue puts every copy behind. A copy set to Ask before updating, the default, shows update available with what changed, raises A calendar from Administration has an update in its agency, and waits for its editors to press Update; a global administrator can also use Push the update… on the catalogue row for chosen agencies, and is told, agency by agency, what happened. Several changes while a copy is behind are one update to the latest. A copy set to Update automatically changes with the catalogue, with a change-log row and an Activity entry in its agency. Either way, an update the agency's own bindings forbid — one that would make a freeze calendar of a calendar the agency names as an Allow — is not applied: the copy reads update blocked and says why.

Forbid and Allow. A job or workflow may name calendars to Forbid (do not start on these days) and to Allow (start only on days in one of these), from its own agency's calendars and copies; a schedule entry's own calendars are called Forbid and Allow too. A freeze calendar is never an Allow, and one calendar in both lists is refused. They gate every automatic start — a schedule, a service account's trigger, a reaction, a file arrival — but not a person's Run, and a start they stop is dropped and recorded, never postponed. The user manual has the full rule.

What you cannot author in the app, and why

Scripts. There is no in-app script editor and there will not be one. Automation content belongs in version control, where it can be reviewed, diffed, blamed and rolled back.

Every question of the form "why can I not edit this here?" traces back to that decision or to the source of the definition in front of you.

Git sync, and what it will not touch

Sync brings definitions in from each agency's own repository. It deliberately leaves the app-owned sidecars alone: tags, notes, a scope's runner bindings and a workflow's canvas layout survive every sync, because they are yours rather than the repository's.

The Git Sync and Schedule Pushes tabs in History are where you look when a definition is not what you expected — before assuming the app is wrong.

Two lines a Git job may still carry, and what happens to them

Older job files, and script sidecars, may say executor: or runner_tag:. Both once decided where a job ran. Neither is read any more: where a job runs is decided by its scope's agency and the scope's runner binding (A3), and by nothing on the job.

Neither line is an error, whatever its value — sync does not fail and the job still runs. Each is ignored with a warning, in the sync log and from cronomicon validate. The Notices inbox lists the jobs that still say executor, and the ones that say runner_tag on a scope that is not bound.

Do not leave them there. A line that reads executor: ssh looks like a promise that the job stays on the server, and it is not one. If an author meant it, the promise is kept by binding the scope; then remove the line, and the notice clears at the next sync.

A7 · External triggers, and what Cronomicon does not do yet

Two things administrators get asked about, in one module: letting other systems start jobs, and the honest list of gaps.

Service accounts

A token is a principal, not a bypass

A service account carries a role and a territory exactly like a person does, and its actions are audited under its own name. There is no second, weaker authorization vocabulary for machines — which means everything you know from A4 applies unchanged. That includes who may mint one: an agency's administrators create service accounts for their own agency, under the same rules as any grant.

The token is shown once, at creation. Treat that moment accordingly.

A job must opt in to being triggered externally

Holding a valid token is not enough: the job itself must be marked as externally triggerable. Being reachable from outside is a decision the job's author makes, not a default that a token can override.

So an over-broad token still cannot start a job nobody meant to expose.

The four not-yets

Say these out loud to your operators before they find them. Each has an interim answer, and all four are on the roadmap.

Email triggers — no native support

Automate Schedule conditions that watched a mailbox have no direct equivalent. The interim answer is a small bridge that turns an inbound message into an API trigger call — which works today, using the service accounts above.

High availability — no standby server

The largest architectural difference from Automate Schedule. Cronomicon runs as a single process, so the answer today is recovery, not failover: backups, snapshots, and a documented restore.

The thing to actually do about it: rehearse the restore. An untested backup is a belief, not a recovery plan, and this is the gap where that distinction costs the most.

Reports — no report builder

You have the Dashboard's Score, filterable History, run analytics, and a CSV export. One caveat worth knowing before you promise anything: the export covers audit records, not run history.

SNMP monitoring — a different shape

Cronomicon exposes Prometheus metrics rather than SNMP. If your monitoring is SNMP-based you need a bridge; the metrics themselves are there.
