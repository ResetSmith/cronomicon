Runner management guide (R7.2)

Day-2 operations for a Cronomicon runner agent (cronomicon-runner) that is already installed and registered. For the initial install + configure walk-through, see runner-install.html; for the credential-model posture and blast-radius record, see runner-security.html. The Runners view also lists the local runner — the server itself, running shell jobs — which is not an agent; §1 says what its row is, and where this guide says runner without qualification it means an agent.

This guide covers, in order: checking status & health, managing a runner day-to-day (drain / kill / token hygiene), updating the agent binary, re-syncing a runner's config and identity with the server, and removing / retiring a runner.

One concept to hold first — declared vs local config. A runner declares name, os, capabilities, maxConcurrent, inventory, version, and its protocolVersion to the server only at registration (POST /api/v1/runners/register). The poll loop sends nothing but the bearer token — it is a heartbeat and a kill/drain channel, not a config update. So the server's view of a runner is frozen at its last registration. Anything that changes those declared fields — including upgrading the binary (which changes version/protocolVersion) — only reaches the server when the runner re-declares. On a protocol v4+ agent (0.47.5+) this is automatic: the agent sends a digest of its declared config with every poll, so a change propagates on the next poll after a restart — the server spots the drift and requests the re-declare itself. The Runners → Resync button remains as a force-lever (see "Resync"). Local fields (keys, known_hosts, CA, poll cadence, fan-out, local inventory) need only a restart, or take effect on the next run.

1 · Check status & health

On the host (systemd):

systemctl status cronomicon-runner          # running / failed, recent log lines
systemctl is-active cronomicon-runner        # active | inactive | failed
journalctl -u cronomicon-runner -f           # tail the agent log
journalctl -u cronomicon-runner --since '1 hour ago'
/usr/local/bin/cronomicon-runner version     # build version + commit

On the host (container):

docker ps --filter name=cronomicon-runner    # Up / Exited
docker logs -f cronomicon-runner-01
docker exec cronomicon-runner-01 cronomicon-runner version

Healthy logs show registered with server (first start) or resumed runner identity (restart), then steady poll activity on the cadence. A target dial that fails host-key verification surfaces per-host; a server reap shows server returned 404 on poll — re-registering.

On the server (the Runners view): each runner shows a status, its load (active runs / maxConcurrent), declared capabilities, version, last-seen time, an inventory chip, and its Agency: the agency that owns it, which is also the one agency whose runs it takes (§4.9). Status meanings:

StatusMeaning
onlinePolled within the offline threshold; claiming work.
degradedStill online, but its last heartbeat is more than 2 minutes old — two missed polls — or it registered and has never polled. Derived when the row is read, never stored, so it is a freshness reading laid over the lifecycle status rather than a state the runner enters. It names the window in which a runner that had already died still read online: offline is only declared at the 5-minute threshold below. Dispatch and claiming are unaffected; the UI treats a degraded runner as reachable and keeps its recovery actions offered.
drainingAsked to drain — finishing active runs, claiming nothing new.
offlineNo heartbeat for CRONOMICON_RUNNER_OFFLINE_AFTER (server default 5m, ≈5 missed 60s polls). The reaper reconciles its in-flight runs to a terminal failure with runner_lost (History shows a Lost badge).

A runner that stays offline for CRONOMICON_RUNNER_DEREGISTER_AFTER (server default 14d) is deleted by a secondary sweep. An offline runner that comes back resumes its ID (D4) and flips to online on its next successful poll.

Click any runner row to expand its detail panel. The compact row carries only Test and Deregister; the remaining per-runner actions — ⚙ Edit (managed settings), Resync, Scan keys, Drain and Copy upgrade command — live in the expanded detail. A runner is managed by its owner. Every one of these, and every edit in the panel, needs configureApp on the agency that owns the runner; a Global runner is a global administrator's. Someone who administers a different agency sees the buttons disabled, with a tooltip naming whose runner it is. (The one exception is Scan keys on a runner that serves an agency other than its owner, §4.6.) Beyond ownership, the gating follows one rule: Resync, Scan keys and Drain are offered while the runner is reachable — online or degraded, because a degraded runner still heartbeats and still holds work, and that is the state where you most need them. offline still hides them: there is nobody there to ask. There is no protocol-version gate on these buttons: the server's protocol floor tracks the current wire protocol, so every agent that can talk to this server speaks it. One below the floor is refused at registration, at redeclare and on every poll with 426 protocol_too_old, never silently degraded. Copy upgrade command is always offered whatever the version badge says — it is also the reinstall command, and “up to date” compares version strings, so a locally-built agent can read current while speaking an older protocol. The detail panel also surfaces health-at-a-glance (status, live heartbeat age, load, sandbox posture), the full capability list, registration provenance (with a link to the token that created the runner), a read-only managed-settings summary, an agent-version upgrade hint, the runner's currently-running jobs, its recent job history, its owner and what it serves (§4.9), the scopes bound to it (§4.8), and — full width at the bottom, for the administrators of the agency that owns it — its Trusted host keys (§4.6).

The panel is laid out for readability. It reads top-down as what this runner is, then what you can change: Registration and Managed settings — the two read-only blocks — sit above the sections about where it works and what it may carry (Agency, Scopes served, Tags, Secret injection), so the ⚙ Edit entry point (which lives on the Managed settings header, beside the pending-change dot) is near the top instead of below the fold. Registration facts such as Protocol and Registered are stated once, under Registration. Fields the runner has no value for are collected into a single muted “Not recorded:” line rather than each rendering a labelled —, and background explanation sits behind an ⓘ disclosure on the section it belongs to.

The local runner's row

One row in the registry is not an agent. Local runner, marked this server, is the Cronomicon server itself running shell jobs (bash, perl, powershell, python) over SSH. It is always listed, there is exactly one, and it takes work by the same rules as an agent (§4.7). What differs:

  • It is configured in Settings, not here. A global administrator turns it on or off, sets how many runs it executes at once and chooses the agencies it serves under Settings → Local runner; for a global administrator the row links there. Turned off — as it is on a new installation — or forbidden on the host (CRONOMICON_LOCAL_RUNNER=forbid), the row reads offline, and its expanded row says which of the two it is. With no agent registered and the local runner off, the registry says that nothing can run a job yet.
  • It is Global's, and it is the one runner with a serve list. An agent serves exactly the agency that owns it; the local runner serves every agency a global administrator has listed for it.
  • Nothing in this guide's agent procedures applies to it. It has no Test, Deregister, Resync, Drain or upgrade command and no managed settings; it cannot be deregistered, and the offline and deregister sweeps above never touch it. Its Secret injection line reads Always on: the server is the secret store, so a run it executes gets its secrets without their leaving the process.
  • It never takes a run that binds an SSH key. A bound key is delivered as a file on the machine that runs the job, and only an agent does that (§4.7).
  • Its host keys are approved like an agent's, in the same Trusted host keys panel (§4.6), and it can be bound to a scope like any runner (§4.8).

How the local runner executes a run, its environment variables and its crash recovery are in the Administrator Manual §4.

A second, independent reaper acts on workflow-launched runs. The workflow engine's orphan reaper (a startup sweep plus a 10-minute periodic pass) fails the queued/running child runs of an orphaned or 24h-stale workflow with reason orchestrator_lost — including runs assigned to a perfectly healthy runner. Unlike runner_lost, this shows a plain Failed badge (no amber Lost badge): it means the orchestrator lost track of the workflow (e.g. a server restart mid-workflow), not that the runner vanished.

2 · Manage day-to-day

Drain (graceful — do this before maintenance)

Draining lets active runs finish while the runner stops claiming new work — the safe way to take a runner out of rotation.

  • From the UI: Runners → Drain (the button shows while the runner is reachable — online or degraded). On its next poll the agent stops claiming, lets active runs finish, and exits once idle. Because the generated unit is Restart=on-failure, a clean drain-exit (code 0) leaves the service stopped — bring it back later with systemctl start cronomicon-runner. Starting it back up is the come-back signal: the restarted agent's first poll re-admits it — same id, same key, online and claiming work in one round-trip. There is no separate "activate" step; if you want a runner to stay out of rotation, leave the service stopped (or Deregister to revoke its key entirely).
  • From the host there is no drain. systemctl stop cronomicon-runner sends SIGTERM, and the agent cancels the runs it has in flight and exits once they have unwound (the unit's TimeoutStopSec=300 bounds that). Those runs end as failed or lost. To let work finish, Drain the runner in the UI first and stop the service when its load is 0.

Always drain before maintenance so you don't kill mid-flight runs.

Kill a single run

To stop one run without touching the rest, kill it from the server: the next poll delivers a kill for that specific traceId and the agent cancels just that run's execution/session. Because kill and drain arrive only on a poll, the agent keeps polling while executing — a busy runner is still controllable.

Registration-token hygiene is not a kill-switch

Registration tokens are single-use per install (minted from the Runners view; each dies on its first successful registration and records which runner consumed it). Revoking an unused token only stops the install that would have used it. Runners that already registered keep their long-lived crn_run_* key and keep working until you deregister them (see "Remove"). To revoke a specific runner, use its Deregister button — token hygiene never touches registered runners.

No hot reload

The agent has no SIGHUP/config-reload path — only SIGINT/SIGTERM (drain). Every config change needs a restart (systemctl restart cronomicon-runner); the restart is also all a declared-config change needs — drift detection re-declares it on the next poll (see "Resync").

3 · Update (upgrade the agent)

Keep agents and the server in lock-step across upgrades. The wire protocol is versioned with a server-enforced minimum (runner-security.html §4); a drift becomes a loud, diagnosable failure rather than silent mis-driving.

Upgrading the server to 2.2.0 or later means upgrading every older runner with it. 2.2.0 moved the runner protocol from 13 to 14 (host-key removal and the known_hosts report, §4.6), and it has not moved since: an agent from 2.2.x keeps polling a 2.3.0 server and taking work, though agents and server should still be kept on the same release. A runner still on protocol 13 is refused with 426 protocol_too_old on its next poll and takes no work until it is upgraded. Nothing is lost: its row, owner, tags, scope bindings and approved keys stay as they are. The fastest path per host is Copy upgrade command in the runner's expanded row on the Runners view, run as root on that host — it downloads this server's agent binary, verifies it against SHA256SUMS, swaps it in (keeping the old one at .prev) and restarts the service. Container runners: pull the image tag that matches the server and recreate, as below.

What upgrading the server to 2.3.0 changes for an agent that is already enrolled. Nothing on the host: no flag, no file, no restart beyond the upgrade itself. On the server, every runner gets an owner from what it served before: an agent in one agency is now owned by that agency and managed by its administrators; an agent in no agency is owned by Global and serves Global; an agent that was in several agencies is a legacy placement — it takes the same runs as before, and is a global administrator's until it is settled (§4.9). Two things can move work, and the upgrade raises a notice for each scope it affects: a shell job that used to run from the server may now be taken by an agent that serves its scope's agency, and the reverse (§4.8).

An upgrade is per machine, not per runner. Every agent on a host shares the one binary (runner-install.html §3), so replacing it means restarting all of them: the default unit and each cronomicon-runner-<name>.service. The Copy upgrade command on any of the machine's rows does that — it swaps the binary once, restarts every agent unit that is enabled or running, watches them for 20 seconds and reports each one by name. A unit is reported OK only when it is still running at the end of the watch as the same process: an agent that exits a few seconds in is started again by systemd, and would otherwise look healthy. A restart cancels whatever a unit has in flight, so Drain every agent on the machine first, not only the row you copied the command from, and run the command when their load is 0. By hand, the steps below apply to each unit: systemctl list-unit-files 'cronomicon-runner*.service' lists them.

What upgrading an agent to 2.3.0 changes on its host. Two things. What it claims: an agent that names no capabilities now claims all four shell types (bash, perl, powershell, python) whatever is installed on its host, because those jobs run on the targets; before, it claimed a shell type only when the interpreter was on its own PATH. So an auto-detecting agent with no local perl, pwsh or python starts taking those runs after it restarts, and its row shows the new capabilities. Ansible and Terraform are detected on the host as before, and an agent with an explicit -capabilities list is unchanged; name the list to keep a type off an agent. Its unit: the upgrade command adds SystemCallErrorNumber=EPERM, as a drop-in (/etc/systemd/system/<unit>.d/10-syscall-errno.conf), to every agent unit that filters system calls without it, and says so when it does. Every unit written by an installer older than 2.3.0 is one; the line is what lets the agent find its toolchains on RHEL 8 (§6).

systemd host:

# 1. Drain first so no run is interrupted: UI → Drain, and wait for its load
#    to reach 0. `systemctl stop` alone does NOT drain: it cancels runs in flight.
sudo systemctl stop cronomicon-runner

# 2. Build/copy the new binary and install it over the old one.
cd backend && CGO_ENABLED=0 go build -o cronomicon-runner ./cmd/cronomicon-runner
sudo install -m 0755 cronomicon-runner /usr/local/bin/cronomicon-runner

# 3. Start again — it resumes its identity from the identity file.
sudo systemctl start cronomicon-runner
cronomicon-runner version    # confirm the new build

Container: pull the image tagged with the server's new version (or rebuild your own), then recreate the container against the same named volume so identity persists:

docker pull ghcr.io/resetsmith/cronomicon-runner:2.2.0   # -fat for ansible/terraform
docker stop cronomicon-runner-01 && docker rm cronomicon-runner-01
docker run -d --name cronomicon-runner-01 --restart unless-stopped \
  -v cronomicon-runner-data:/var/lib/cronomicon-runner \
  ...same -e flags as install... \
  ghcr.io/resetsmith/cronomicon-runner:2.2.0

The server keeps showing the OLD version/protocol until you re-register. A restart resumes the stored identity and never re-declares — so after an upgrade the runners row still reflects the version, capabilities, and protocolVersion from the last registration. This matters after an upgrade that changes the protocol version. The server's protocol floor tracks the current wire protocol, so every agent that can talk to this server speaks it: one below the floor is refused at registration, at redeclare and on every poll with 426 protocol_too_old, never silently degraded. So an agent whose binary you upgraded across a protocol bump keeps working, while one you did not upgrade stops receiving work at its next poll and says so in its own log — rather than running on with fields it silently drops. The server picks up a new build automatically on the first poll after the restart (drift detection); the Resync button forces it.

4 · Resync (reconcile a runner with the server)

Resync = re-aligning the server's view of a runner with the runner's actual identity and config. It's needed because declared config crosses the wire only at (re-)registration (see the note at the top). Since protocol v4 the agent can re-declare its current local config in place — same id, same API key, same owner agency, no deregistration, active runs unaffected — and since 0.47.5 the server asks for that automatically: the agent sends a config digest with every poll, and a mismatch with the stored declared set triggers the re-register op on that same poll (flap-guarded to at most one op per 5 minutes per runner). Runners → Resync forces the same op on demand. The button authenticates nothing new: the agent re-reads its own config, so a resync can never change what a runner is from the server side. Pick the case that matches:

Case A — the server reaped/deregistered the runner (automatic)

If the server has deleted the runner (manual deregister, or 14-day offline sweep), the agent's next poll returns 404; it logs server returned 404 on poll — re-registering, discards the stale identity, and re-registers automatically with its current config. Nothing to do — provided the registration token in its env is still valid. Its install token is long dead (single-use, consumed at first registration) — mint a fresh crn_reg_* (Runners → Register New Runner), put it in the runner's env, and restart so the re-register can succeed. This is the one flow that still needs a registration token: the reaped row's crn_run_* key was revoked with it. (The Resync button can't help here — the row is gone and the runner's key revoked; this path always needs a registration token.) The new token decides the owner again, so mint it for the agency the runner belonged to. What comes back is a new runner with a new id: the scopes bound to the old id stay closed until you restore its placement, and the host keys approved for the old id stay on that record until you copy them across (both in §4.8).

Case B — you changed declared config (capabilities / name / os / maxConcurrent / inventory / toolchains)

Checkout-mode capabilities are declared too. The tokens a runner advertises — ansible, checkout (from -allow-checkout), collection:<fqcn> (installed collections), vault (from -vault-password-file), sandboxed (the agent can create a per-run scope, which takes an agent that runs as root) — plus the detected toolchain versions on the Runners page are all captured at registration. So enabling checkout, provisioning a new collection, adding the vault file, or gaining a systemd sandbox does not reach the server on a plain restart: it needs a resync (or re-registration), same as any declared change below.

A plain restart will not propagate these — the agent resumes its identity and skips registration. To propagate:

  • Just restart (preferred): restart the service so the agent is reading the new values (systemctl restart cronomicon-runner). At startup it recomputes its config digest (re-probing toolchains, collections, and the sandbox), the first poll carries it, and the server requests the re-declare automatically — no click needed. The Resync button forces the same thing without waiting a poll (and a newly installed collection is re-detected at re-declare time even without a restart; flag-derived tokens like checkout/vault and the startup sandboxed probe still need the restart first). One caveat: the startup probe is what gets declared — if the agent starts before its toolchain is ready (e.g. ansible on a slow-booting venv), the reduced token set propagates; restart or Resync once the toolchain is healthy (the agent logs the detected set at startup). No registration token involved — the agent authenticates with its existing crn_run_* key.
  • Alternative — deregister, let it re-register: edit the config (e.g. /etc/cronomicon-runner/runner.env), then Runners → Deregister the runner. On its next poll the agent 404s and re-registers with the new config. The old row is gone; the runner keeps the same name but gets a new id, with the consequences for its bound scopes and approved host keys described under Case A. (Restart the service after editing config so it's reading the new values when it re-registers.)
  • Last resort — delete the identity file: drain, stop the service, delete the identity file (e.g. /var/lib/cronomicon-runner/identity.json), then start. The agent registers fresh with the new config. Note this mints a new id; the old runners row lingers as offline until the reaper deregisters it (5m → 14d). Prefer the deregister path so there's no orphan row.

The deregister and identity-file paths need a valid registration token at re-register time; the Resync button does not.

Case C — you changed keys, known_hosts, or local inventory

These are runner-local and not declared to the server, so no re-registration is involved:

  • Key files and known_hosts are read at dial time — editing their contents in place takes effect on the next run, no restart needed. Only changing their paths (the -key-dir / -key-map / -known-hosts config) needs a restart.
  • One key file serves bash AND ansible. A key in -key-dir/-key-map named after the host's authKeyEnvVar is bridged to ansible automatically, so you do not provision the same name a second time as an env var. Each run's log shows what it used: cronomicon: auth: key "NAME" → <path>, cronomicon: auth: --private-key NAME → <path>, and cronomicon: trust: known_hosts → <path>. Prove a name resolves with cronomicon-runner doctor --auth NAME [user@host] before a run; the expanded Runner detail also lists a runner's resolvable key names as chips. (Opt out with -no-auth-bridge.) See runner-security.html §2, "How a runner authenticates."
  • Local inventory (-local-inventory, local mode) is loaded at agent start — edit it, then systemctl restart cronomicon-runner.

Case D — protocol/version drift after an upgrade

This is the "make the server see the new build" follow-up to an Update (§3): the post-upgrade restart is enough — the new binary's first poll carries a changed digest (its version differs) and the server records the new version and protocolVersion automatically; Resync forces it without waiting a poll. Confirm on the Runners view that the version (shown under the runner's name) updated.

4.5 · Managed settings (tune a live runner from its row)

Managed settings are the exception to "declared config crosses the wire only at registration." A third category joins declared and local: a small set of server-managed operational overrides the runner's owner edits on its row — ⚙ Edit on the Managed settings header opens a drawer — that ride to the agent over the poll channel and apply in-memory on the next poll. No SSH, no restart, no env edit.

The managed set is: max jobs (maxConcurrent), the three sandbox caps (MemoryMax/CPUQuota/TasksMax), the checkout policy (allowCheckout + the repo checkoutRepos allowlist), and a subtract-only capability mask (remove run-types from what the runner will claim). Each field is tri-state: set it to override the runner's local value, or leave it blank/inherit to keep the local value. The secrets these depend on — the checkout deploy token and the vault password — are never managed here; they stay in runner-local custody (installed at §3 / runner-install.html), so the server never holds secret bytes.

The sandbox caps need a sandbox. They cap each run in a systemd-run scope of its own, and systemd lets only root create one. An agent set up by the installer runs as its own user: its row shows Unsandboxed, the caps are stored and never applied, and the drawer says so beside the fields. To bound such an agent, limit its unit, which covers the agent and all its runs together, on its machine and with no restart:

sudo systemctl set-property cronomicon-runner.service MemoryMax=4G CPUQuota=200% TasksMax=1024
systemctl show cronomicon-runner.service -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax

Use cronomicon-runner-<name>.service for an instance. The values are kept in /etc/systemd/system.control/<unit>.d/ and win over the unit file's. runner-install.html §3 has the install-time flags and what happens to a run that reaches a limit.

Each write bumps a version; the agent echoes the version it has applied as its poll ack, so the row shows a pending dot (● pending beside Managed settings) until the change round-trips — typically one poll cycle. The capability mask is enforced server-side at claim (a masked run-type is simply never assigned to the runner) and honored agent-side too. Managed overrides do not touch the config digest, so changing one never triggers a drift re-registration (§4).

One row-level flag is deliberately not part of the managed set: Secret injection. It is a per-runner trust decision, not an operational tune, and it lives in its own control on the runner's detail panel behind configureApp on the agency that owns the runner. When it is on, this runner may claim runs whose job or script declares reference bindings, and it receives the resolved secret values in its dispatch manifest; when it is off, such a run is never dispatched to it at all. Grant it only to runners you trust with the secrets of the agency they serve. (The local runner has no toggle: the server resolves the references itself, so its line reads Always on.) Every registered agent speaks the current wire protocol, so an agent that could ignore the manifest's secrets block cannot exist on this server (§4, and runner-security.html §4).

Every registered agent receives managed settings. Delivery is keyed on the settingsVersion param the agent's poll carries, and since the protocol floor tracks the current version there is no agent old enough to be missing it.

4.6 · Trust a target's host key (scan, review, approve)

You do not need to hand-assemble a known_hosts before a runner's first SSH run. Host-key verification is strict — an unknown or changed target key is refused — but you can trust a key at the moment it's actually known, with a record of who trusted it. This also covers ansible runs: local-toolchain runs verify against the same known_hosts the agent seeds here, so an approved key serves both Go-SSH and ansible (no separate ~/.ssh/known_hosts for ansible). Nothing is ever trusted on first connect, on an agent or on the local runner: approving a key here is the only way a runner comes to trust a host. Everything in this section needs configureApp on the agency that owns the runner (a global administrator, for a runner that is Global's); the one exception, for an agency a runner serves and does not belong to, is at the end of the section.

  1. A runner's SSH run to an unverified host fails with a host_key_unverified reason naming the host (the run's status reason). The run is a soft failure — nothing was executed on an unverified host. You do not have to wait for that failure: binding a scope to a runner tells you up front how many of the scope's hosts the runner does not trust yet (§4.8).
  2. On the Runners view, expand the runner and press Scan keys (or Scan keys… on its Trusted host keys panel). The Host keys — <runner> dialog offers four sources:
    • Scan a scope — the runner connects to every host of the scope from where it sits and reports the key each one presents. Only the scopes of an agency the runner serves are offered, and the ones bound to it are marked. A host reached through a bastion cannot be scanned: it is listed as not scanned, with the exact name its pasted line must start with. The bastion itself is scanned.
    • Scan hosts — a typed list, one per line or separated by commas or spaces, as host or host:port.
    • Paste keys — known_hosts lines you already have (checked ssh-keyscan output, a key for a host behind a bastion), one line per key: host key-type key. Up to 500 lines at a time.
    • Copy from a runner — the keys another runner trusts that this one does not. This is the host-key half of replacing a runner (§4.8). The two runners sit in different places on the network, so the same address is not guaranteed to be the same machine: the list is reviewed like any other.
    A scan needs the runner to answer, so both scan sources are disabled while it is offline. Paste keys does not: pasted keys are delivered when the runner returns.
  3. Every source ends on the same review screen, and nothing is trusted before it. Each row shows the host, the full SHA256 fingerprint, the key type and a status: New (nothing is known about this host's key), Matches server (the same key that is approved for the local runner — the server itself — for that host), Already trusted (this runner trusts exactly this key), Changed (differs from the key this runner trusts now, or from the key approved for the server — the old fingerprint is shown beneath) or Cannot accept (an unreadable or refused line, with the reason). Unreadable lines and changed keys sort to the top. Compare each fingerprint out-of-band against the host itself (ssh-keygen -lf /etc/ssh/ssh_host_*_key.pub on the host, or the fingerprint its admin publishes); Copy as text hands you the list for that. The select-all box never ticks a Changed key — each one is ticked on its own — and a key that arrives from a scan after the list opened is marked and left unticked. Then press Trust N keys on <runner>.
  4. The runner receives the approved lines on its poll, usually within a few seconds, appends them to its known_hosts (idempotently — a re-delivery never duplicates) and reports the file back. Retry the run; it now verifies.

Reject the scanned keys you can't verify (Reject N selected) — a rejected key is never trusted, and the rejection is recorded. Approving a key you have not compared trusts whatever answered on that address (the scan only shows what the host presented, not that it wasn't already compromised) — see runner-security.html §5. Keys a runner has scanned and nobody has reviewed are listed on the Runners view, under the registry, as Host keys awaiting review — per runner, for the runners you may review, with a Review button; until they are approved, that runner's runs on those hosts fail at the first connection.

A paste is accepted whole or not at all. The server parses every line itself, computes the fingerprint from the key, and writes the line the runner receives — nothing typed reaches a runner's file verbatim. A line with a wildcard or negated host (*, ?, !), a @cert-authority or @revoked marker, or a host the runner's verifier could not look up is shown as Cannot accept, and the paste cannot be committed until it is corrected or removed. A commit is also bound to what you reviewed: if a key changed between the review and the click, or would replace a trusted key you did not tick as changed, it is refused (409 review_stale) and the list is shown again.

The Trusted host keys panel

Each runner's expanded row ends, for the administrators of the agency that owns it, with a full-width Trusted host keys panel. Its buttons — Scan keys…, Paste keys… and Copy from a runner… — open the dialog above on that source. For an agent it holds two lists that are deliberately not merged:

  • Approved in Cronomicon — the keys an operator approved for this runner: host (and the scope it was scanned for), fingerprint, key type, source (Scanned, Pasted, Carried), who approved it and when, and its state on the runner: Not yet sent, Sent (the runner has not reported since), In the file, or Not in the file. A key that is not in the file gets a Send again button; a banner counts them, because runs on those hosts will fail. History underneath lists what is no longer in force: Replaced, Rejected and Removed decisions, each with who made it.
  • Present in the runner's known_hosts file — what the runner itself reported from its own file, line by line, and when. Each line's origin is Approved here, Not approved here (it reached the file some other way — a pre-seeded file, an edit on the host — and the runner trusts it all the same), Revoked (a @revoked line) or Certificate authority (a @cert-authority line). A hashed entry is shown as hashed entry: its name cannot be recovered, only its key type and fingerprint. The runner reports when it starts and after every change made from here; Ask for a fresh report requests one. Only fingerprints cross the wire, never the file, and a report carries the first 5,000 entries.

A changed key replaces the old one. Approving a Changed key retires the previous approval for that host and key type, and the runner is told to delete the old line as well as add the new one — a rotated host key no longer leaves its predecessor trusted. Remove does the same without a replacement: after a confirmation, the runner drops the line on its next poll and its runs on that host fail until a key is approved again. The agent removes only a line that names that one host with that key; a hand-written line naming several hosts is left alone and keeps showing in the file list.

Every approval, rejection and removal is kept as a row with the runner, the actor, the source and a batch id, and each batch writes one Host Keys row to the Change Log whose Show keys link opens the keys of that change. A key stays on record for as long as it is trusted; rejected, removed and replaced rows are pruned after the Host Key History window (Settings → Audit & Compliance, 365 days by default). A pre-seeded known_hosts (--known-hosts at install) still works and skips the scan for hosts you already trust — its lines appear in the second list as Not approved here.

The local runner's host keys

The server trusts a host the same way an agent does, and only that way: expand the Local runner row and use the same Trusted host keys panel and the same review screen. The differences follow from there being no agent and no file:

  • The record is the trust store. The local runner verifies every connection against the approved keys listed here, so an approval is In force the moment it is made and a removal takes effect at once. There is no second list, no Send again and no report to ask for.
  • It scans from the server, whether it is turned on or not — scanning is not running a job.
  • A bastion is verified too, under the address its record is dialled at. A host behind a bastion is not scanned; paste its key.
  • A run that reaches a host with no approved key fails for that host with host_key_unverified — the local runner has no approved host key for <host> — scan it and approve its key under Runners → Local runner → Host keys. Test connection on Settings → SSH Targets reports unverified for the same reason, and no longer captures a key. The notice The local runner has no approved key for some hosts lists what is missing, scope by scope.
  • Only a global administrator decides its keys. The server's trust in an address is one fact for every agency it serves, so an agency administrator may scan their own scope with the local runner, and what the scan finds then waits for a global administrator to approve.
  • One key per address and key type. Two different machines that share an address behind two different bastions cannot both be trusted by the local runner.

The keys the server had already recorded for its host records before 2.3.0 were carried over by the upgrade and are listed with the source Carried. Where two records for one address held different keys, one is trusted and the notice Two records for one address had different host keys names the other.

Reviewing keys on a runner that is not your agency's

An agent's host keys are its owner's to decide. The exception is for a runner that serves an agency it is not owned by — the local runner, and a legacy placement (§4.9) — so that a department does not wait on a global administrator for every new host. An administrator of an agency such a runner serves can open the Host keys dialog for it — Scan keys on an agent's row, or, for a scope of theirs that is bound to the runner, Scan this scope… on that scope's row on the Scopes page (§4.8), which is the way in for the local runner — narrowed to one thing:

  • They may scan a scope of their own agency with the runner, and see the keys that scan found. Scanning typed hosts, pasting keys, copying from another runner, removing a key and reading the runner's record stay with the owner.
  • On an agent they may approve a first key — for a host the runner has no key for, of any type. A key that would replace one the runner already trusts, or that differs from the key approved for the server, is the owner's decision; the review screen says so and the server refuses it (403 owner_required).
  • On the local runner they approve nothing: the scan's findings wait for a global administrator, as above.

4.7 · Tags — labels, and only labels

A runner's tags are free-text labels you set on its row (expand the runner, edit the tag chips; configureApp on the agency that owns the runner). They help you find and group runners in a long list, like the tags on jobs, scripts, schedules, workflows and scopes. Nothing is dispatched on a tag. No claim, gate or warning reads one, so adding, renaming or removing a tag never changes where work runs.

This changed in 2.2.0. Earlier releases let a job, or a single run, be pinned to a runner tag (runner_tag: in the job's YAML, a field in the composer, a Run on control in the Run dialog). All three are gone. “Only this runner reaches these hosts” is a fact about where a scope's hosts are, so it is now recorded on the scope, by an operator, as a runner binding (§4.8). A runner_tag: line left in a Git job file is ignored with a warning — in the sync log, in cronomicon validate, and, when the job's scope is not bound, as a notice in the Notices inbox (the Scopes page shows a banner that points there). Old runs still show Pinned to runner tag in History.

What does decide where a run lands. Nothing on a job, a script or a run chooses its runner. A run is queued, and the first eligible runner that asks takes it — an agent, or the local runner. Eligible means all of these hold, none of them a tag:

  1. Agency. The runner serves the agency of the run's scope. An agent serves exactly the agency that owns it; the local runner serves the agencies listed on its setting. A run with no scope belongs to Global, and only a runner that serves Global takes it.
  2. Scope binding. If the scope is bound to runners (§4.8), the runner is one of them.
  3. Capability. The runner can run the run type and advertises every token in the job's requires (vault, checkout, a collection…). The local runner runs only the shell types and advertises no tokens. requires is read for shell jobs as well as Ansible ones.
  4. Secret injection. A run that carries reference bindings goes only to an agent with the Secret injection flag (§4.5). The local runner resolves them itself, on the server.
  5. SSH key bindings. A run that binds an SSH key — declared on the job or script, or added in the Run dialog — is never taken by the local runner: the key is delivered as a file on the machine that runs the job, and only an agent does that. (The Connect as identity a run connects with is a different thing and works on the local runner.)

So where an agent and the local runner both serve an agency, a shell job on an unbound scope may be taken by either, run to run. History names the one that took each run in its Runner column. To decide, bind the scope.

4.8 · Scopes served — binding, replacing and restoring a runner

A scope can name the runners allowed to serve it. An operator with configureApp on the scope's agency sets this on the Scopes page: expand the scope, and under Runners press Bind runners… (or Change…). The dialog lists every registered runner, agents and the local runner alike; one that does not serve the scope's agency is shown disabled with the reason. It previews what saving will change before the save is allowed. Binding needs authority over the scope and a runner that already serves its agency — not authority over the runner — so an agency can bind its own scope to the local runner, which is Global's, once a global administrator has made it serve that agency.

  • A scope with no bound runner is unrestricted: any runner that serves its agency may take its runs — the agency's agents, and the local runner if it serves the agency.
  • A bound scope's runs are claimed only by its bound runners. The binding narrows and never widens: it is applied on top of the agency, capability, secret-injection and key-binding rules (§4.7), never instead of them. Runs already queued follow a change of binding.
  • Binding is the one way to decide where a scope's jobs run. Nothing on a job or a run chooses a runner, and a shell job on an unbound scope may be taken by an agent or by the server, run to run. Bind the agents that reach the hosts to keep a scope's jobs off the server; bind the local runner to keep them on it. Whichever runner takes a run uses its own keys and its own approved host keys.
  • A job that binds an SSH key needs an agent among them. The local runner never takes such a run. If the binding leaves no registered agent serving the scope, the run is refused: 422 key_binding_requires_runner on a manual or token trigger, a skipped row on a schedule, a failed step in a workflow.

This changed in 2.3.0. Earlier releases had two executors, and a job, a script, a global default or a single run could choose between the server (executor: ssh) and a runner; a bound scope then implied the runner and refused an explicit ssh (scope_requires_runner). All of that is gone. An executor: line left in a job's or a script's YAML is ignored with a warning — in the sync log and in cronomicon validate — and a notice lists the Git jobs that still carry it. The upgrade also raises a notice for each scope whose shell jobs ran in one place and may now be taken in another (Shell jobs that ran from the server may now run on an agent, and its two siblings): bind the scope to the runners that should serve it, then dismiss the notice.

The preview names the runners that will stop and start taking the scope's runs, the jobs that bind an SSH key when no agent would be left to serve the scope, and, per chosen runner, what it is missing: a run-type the scope's jobs need, the secret-injection grant, and how many of the scope's hosts it does not trust yet. Trust belongs to the runner, so scan the scope from each bound runner and approve the keys (§4.6) before the first run. The scope's expanded row keeps a per-runner line — N of M hosts not yet trusted by <runner> — with a Scan this scope… button until the gap is closed.

On the Runners view, each runner's expanded row has a Scopes served section listing the scopes bound to it; with none, it says the runner takes any run of the agency it serves. Bindings are edited on the scope; this section states the consequence — if the runner goes offline or is removed, those scopes' runs wait, they do not move to another runner by themselves — and offers the one-step hand-over.

Replace this runner…

Replace this runner… (in Scopes served, and as a replace link beside a deregistered runner on the Scopes page) binds every scope bound to the runner to a runner you choose instead, in one step. Like any binding it is judged on the scopes: you need configureApp for every scope the old runner is bound to, and the replacement must serve each of those scopes' agencies; if it does not for any one of them, nothing changes and the scopes in the way are named. Since an agent serves one agency, a legacy placement bound to scopes of several agencies cannot be replaced by one agent in one step — re-bind each agency's scopes to that agency's agent on the Scopes page (§4.9). Host keys are not handed over with the scopes. After the replace, a notice offers Copy host keys to <replacement>…, which opens the review screen on the keys the old runner trusted (source Carried) — or scan the scopes from the replacement instead.

When a bound runner goes away

A binding outlives its runner. Deregistering a bound runner, or letting the offline sweep reap it, does not unbind its scopes: a scope confined to one network segment would otherwise quietly reopen to every runner that serves its agency, the server included. The scope stays bound to the runner by name, shown as <runner> · deregistered; nothing claims its runs; and each waiting run records why — scope <scope> is bound to <runner>, and no bound runner is registered any more — restore its placement or bind another runner. Only an operator unbinds.

A re-enrolled runner is a new runner. Its identity is minted at registration, so a host that registers again gets a new id, with no tags and no scopes bound to it. Its agency is whatever its new registration token names (runner-install.html §1) — nothing restores an agency, so mint that token for the agency the runner belonged to. When a runner with the same name was removed earlier and scopes of this runner's own agency are still bound to the old registration, its row is marked bindings to restore and its Agency section shows Previous placement found: when and how the old runner was removed, the tags it held, the scopes still bound to it (so their runs are waiting), and whether the source address matches. Restore placement re-points those scopes at this runner and merges the old tags into its own. It changes nothing about what the runner serves, and it leaves alone any binding the old registration holds on another agency's scope: that scope stays closed until its own agency re-binds it. The offer is made to the runner's owner, who may also Dismiss it — except while the old registration still holds another agency's scopes, when the offer is that agency's too and a dismissal is refused. The name is self-declared by the agent, so when only the name matches, confirm it is the same machine before restoring. The approvals recorded under the old registration are not moved automatically either. While the offer is on the row, the Trusted host keys panel's Copy from a runner… lists the previous registration as a source, so copy the keys (they go through the same review) before you restore or dismiss the placement. The runner's own known_hosts file is untouched by a re-enrollment; until the approvals are copied its lines show as Not approved here.

4.9 · Owner and serves — and settling a legacy placement

Every runner has an owner: the agency whose administrators manage it. What it serves is the agencies whose runs it takes. For an agent the two are one fact — an agent serves exactly the agency that owns it — and it is fixed by the registration token the agent enrolled with (runner-install.html §1). The registry shows it as one chip in the Agency column, and the expanded row's Agency section as an Owner and a Serves line with nothing to edit.

  • There is no membership editor. Before 2.3.0 a runner could be placed in any number of agencies from its row (the Groups editor), and a runner in none served a general pool. The editor is gone, and so is the pool: what used to be "no agency" is the Global agency, a Global agent is a global administrator's, and it serves Global's runs only.
  • There are no shared agents. To serve another agency, enrol an agent for that agency. A global administrator serves an agency that has no machine of its own by deploying an agent with a token minted for that agency; the agency owns it from then on. An agent per agency does not have to mean a machine per agency: a second agent runs beside the first on the same host, under an OS user of its own (runner-install.html §3, --instance).
  • An agent does not move. To put a machine in another agency, deregister it and enrol it again with a token for that agency.
  • The local runner is the one runner with a serve list (§1): Global's, serving the agencies a global administrator lists under Settings → Local runner.

Legacy placements

An agent that was in several agencies when the server was upgraded to 2.3.0 is a legacy placement. It keeps working exactly as it did — the same runs, with the same keys and toolchains — so the upgrade stops nothing. What changed is who manages it: it is Global's, so only a global administrator can change it, where before any of its agencies' administrators could. Its row carries a legacy mark in the Agency column and a Legacy placement chip beside its Serves list, and the notice A runner that serves agencies it is not owned by lists it in the Notices inbox until it is settled.

A legacy placement can be narrowed and never widened. The × on an agency's chip stops the runner serving that agency, after a confirmation; the agency cannot be added back. Once the runner serves a single agency, Hand to <agency> makes that agency its owner, which ends the legacy placement and clears the notice. Neither can be undone from here: the way back is to deregister the runner and enrol it again.

Settle one in this order. The order matters because a scope stays bound to the old runner when an agency is taken off it, and a bound scope whose runner no longer serves it is closed: its runs wait.

  1. Enrol an agent for each agency the runner serves (+ Add Runner, For <agency>), and provision it as that agency's runner: keys, secrets, the Secret injection flag where its runs need it. The new agents can live on the same machine as the old runner: give each an Instance name (runner-install.html §3).
  2. Re-bind each of that agency's scopes to its new agent, scope by scope, on the Scopes page (§4.8). The agency's own administrators can do this. Replace this runner… does not fit here: it moves every scope at once to one runner, and one agent cannot serve several agencies.
  3. Copy the approved host keys for that agency's hosts to the new agent: its Trusted host keys → Copy from a runner…, choosing the old runner, then review the list (§4.6). The copy reads the old runner's record, which is Global's, so a global administrator makes it; the agency can instead scan its scopes from the new agent and approve what it finds.
  4. Then narrow the old runner — take the agency off it — or, when every agency has moved, deregister it.

The order keeps a bound scope from closing; it does not by itself keep runs from failing. A new agent takes its agency's unbound scopes from the moment it enrols, and a re-bound scope's runs go to it alone, so until it has its auth keys and approved host keys those runs fail (host_key_unverified). Nothing stops you copying the host keys (step 3) straight after enrolling (step 1), and that is the safer sequence.

Until then, the administrators of an agency a legacy placement serves can still scan their own scopes with it and approve a first key for a new host (§4.6); everything else on its row is a global administrator's.

5 · Remove / retire a runner

Retire one runner (keep the host)

# 1. Drain (UI → Drain, or stop, which drains on SIGTERM).
sudo systemctl stop cronomicon-runner
# 2. Deregister on the server: Runners → Deregister.
# 3. Delete the identity so a stray restart can't resume the (now-gone) row.
sudo rm -f /var/lib/cronomicon-runner/identity.json
# 4. (optional) keep it from coming back on boot:
sudo systemctl disable cronomicon-runner

Order matters: drain → deregister → delete identity. Deleting the identity without deregistering leaves an offline row to be reaped; deregistering without deleting the identity lets a restart re-register the runner right back.

Fully uninstall from the host (reverse of runner-install.sh)

sudo systemctl disable --now cronomicon-runner
sudo rm -f /etc/systemd/system/cronomicon-runner.service
sudo rm -rf /etc/systemd/system/cronomicon-runner.service.d   # a drop-in an upgrade added, if any
sudo rm -rf /etc/systemd/system.control/cronomicon-runner.service.d   # limits set with set-property, if any
sudo systemctl daemon-reload
sudo rm -f /usr/local/bin/cronomicon-runner
sudo rm -rf /etc/cronomicon-runner          # config (runner.env)
sudo rm -rf /var/lib/cronomicon-runner      # state: identity + keys + known_hosts
sudo userdel cronomicon-runner              # remove the service account
sudo groupdel cronomicon-runner             # if it has no other members

Then Deregister the runner on the Runners view if you haven't already. On a machine with several agents, do not remove the binary while another agent still uses it, and see the next section for removing one of them.

Remove one agent from a machine that runs several

An agent installed with --instance <name> (runner-install.html §3) owns a unit, a user, a group and two directories, all named cronomicon-runner-<name>. Remove them in this order:

# 1. Drain it in the Runners view and wait for its load to reach 0, then stop
#    and disable its unit (a stop on its own cancels runs in flight).
sudo systemctl disable --now cronomicon-runner-tax

# 2. Deregister the runner in the app: Runners → its row → Deregister.

# 3. Remove what the install created.
sudo rm -f /etc/systemd/system/cronomicon-runner-tax.service
sudo rm -rf /etc/systemd/system/cronomicon-runner-tax.service.d   # a drop-in an upgrade added, if any
sudo rm -rf /etc/systemd/system.control/cronomicon-runner-tax.service.d   # limits set with set-property, if any
sudo systemctl daemon-reload
sudo rm -rf /etc/cronomicon-runner-tax        # config
sudo rm -rf /var/lib/cronomicon-runner-tax    # state: identity + keys + known_hosts
sudo userdel cronomicon-runner-tax
sudo groupdel cronomicon-runner-tax           # if userdel left it

The order matters. An agent that is deregistered while it is still running discards its identity and tries to enrol again with its spent token, and keeps trying. Stopping it first avoids that; stopping and disabling it is what keeps the next upgrade of the machine from starting it again (an upgrade restarts every agent unit that is enabled or running). Leave /usr/local/bin/cronomicon-runner in place for the machine's other agents. If the agent's scopes are bound to it, re-bind them first (§4.8): a binding outlives its runner, and the scope stays closed.

Container

# Drain first (UI → Drain), then:
docker stop cronomicon-runner-01            # SIGTERM → graceful drain (up to the stop timeout)
docker rm cronomicon-runner-01
docker volume rm cronomicon-runner-data     # destroys identity + keys — only when fully retiring

Retire a compromised runner (segment-local rotation)

Because custody is distributed (model b), retiring a compromised runner is a segment-local rotation, not an estate-wide one (runner-security.html §7):

  1. Deregister it on the Runners view (revokes its server access).
  2. Delete its identity file (the crn_run_* bearer) so the host can no longer act as that runner.
  3. Rotate the SSH keys it held — only the keys for that runner's segment are exposed; other runners' keys and the control plane's secrets are not.

5.5 · Online, but nothing runs on it

Registration and eligibility are separate things. A runner can be online, healthy and idle while a department's runs queue beside it — because Cronomicon ships names, not values, and claiming is gated on properties an operator has to set (the five conditions in §4.7). Treat an agency as a provisioning domain: a department's agents carry that department's key-dir, secrets and sidecar templates, and because an agent serves only the agency that owns it, a run only lands where its names resolve.

You do not have to guess which gate. A run that no online runner can claim records the reason, computed when it is enqueued and stored on the run, so it still answers the question days later — “why didn't it run last night?” cannot be settled by inspecting today's fleet, because the runner that was missing may be online now.

After changing a runner's capabilities or provisioning, Resync (§4) or restart the agent so it re-declares; queued runs are re-evaluated on the next claim sweep and need no re-trigger.

6 · Troubleshooting — installed & running, but not in the UI

A runner appears in the Runners view the instant POST /api/v1/runners/register succeeds — there is no approval gate. So a service that is "active (running)" but never shows up means registration never completed. The agent logs every startup phase before it runs it, so the last line in the journal names exactly where it stopped:

journalctl -u cronomicon-runner -n 40 --no-pager

The healthy startup sequence is:

runner agent starting
probing tier-2 sandbox availability (systemd-run)     # or: sandbox probe skipped (NoSandbox set)
detecting host capabilities (toolchain probes)
registering with server
registered with server id=…
runner agent online

Whichever … line is last with nothing after it is the phase that stalled or failed. Match it:

Reachability check from the host

curl -sS -o /dev/null -w 'healthz %{http_code} %{time_total}s\n' https://SERVER/healthz
curl -sS -m 20 -X POST https://SERVER/api/v1/runners/register \
  -H 'Authorization: Bearer crn_reg_dummy' -H 'Content-Type: application/json' -d '{}' -i | head
# Expect a FAST JSON 401 (unauthorized). An HTML/login page ⇒ SSO proxy intercept;
# a hang/timeout ⇒ the network or proxy is black-holing the register endpoint.

Silent startup hang (no logs after starting, SIGKILL after the stop timeout)

On RHEL 8 (systemd 239), check the unit first. A unit written by an installer older than 2.3.0 filters system calls without SystemCallErrorNumber=EPERM. That systemd kills the thread making a call its filter list does not know, and the agent's lookup of bash, ansible or systemd-run on $PATH makes one: the lookup never returns, and the log shows sandbox probe did not finish within its deadline and PATH lookup timed out — treating tool as absent. What follows depends on the agent. A 2.3.0 agent starts slowly and comes up without its local toolchains: no ansible, no terraform, no sandbox, so those runs stay queued while shell runs are taken. It looks healthy, so it says what happened in three places: its row on the Runners view reads could not check for ansible, terraform under its capabilities; its journal has could not look for local toolchains at error level; and the self-check that runs before every start prints [FAIL] path-lookup. An older agent with no capabilities set exits with capability auto-detect found no run-type toolchains on PATH and restarts for ever. The fix is the one line. Copy upgrade command (§3) adds it to every agent unit on the machine that lacks it. By hand, for each unit — cronomicon-runner, and cronomicon-runner-<name> for each instance: sudo systemctl edit <unit>, add [Service] and SystemCallErrorNumber=EPERM, then sudo systemctl restart <unit>. Do not re-run the installer on an enrolled agent to get it: the installer needs a new registration token, and it writes runner.env afresh from the flags it is given.

If the agent logs the runner agent starting banner (and maybe a probing…/detecting… line) and then nothing, and systemd eventually reports stop-sigterm timed out … Killing with status=9/KILL, it is blocked inside a startup probe. The overwhelming cause is exec.LookPath — which stats every $PATH directory — hitting a directory on a hung mount (stale NFS / autofs to an unreachable server), where the stat() blocks uninterruptibly. Confirm the exact frame (Go dumps every goroutine's stack on SIGQUIT):

systemctl kill --kill-who=main --signal=SIGQUIT cronomicon-runner
journalctl -u cronomicon-runner --no-pager | grep -A20 'goroutine 1 \['
# A frame in probeSandbox / detectRunTypes / exec.LookPath confirms it.

Find the stuck directory:

PID=$(systemctl show -p MainPID --value cronomicon-runner)
tr '\0' '\n' < /proc/$PID/environ | grep '^PATH=' | cut -d= -f2 | tr ':' '\n' \
  | while read d; do printf '%-24s ' "$d"; timeout 3 stat "$d/." >/dev/null 2>&1; echo "rc=$? (124=HUNG)"; done
timeout 5 df -h    # if df itself hangs, a stale network mount is the culprit

Mitigations, in order:

  1. Repair or unmount the stale mount — this is the real fix. Playbook runs resolve their toolchains through the same PATH, so a hung directory breaks runs too, not just registration. A runner on such a host can register but cannot reliably execute.
  2. Pin a clean PATH in runner.env that omits the hung directory (keep wherever which ansible systemd-run actually resolve), then restart. runner-install.sh (recent releases) does this automatically at install time and prints which directories it excluded.
  3. CRONOMICON_RUNNER_NO_SANDBOX=true skips the systemd-run probe specifically — useful when systemd-run itself stalls (e.g. a non-login system user with no reachable manager) rather than a broad PATH problem.

The agent bounds every startup probe with a deadline, so a hung mount degrades a probe (logged: PATH lookup timed out — treating tool as absent) instead of wedging startup — the runner registers and runs unsandboxed. The stale mount still needs repair for playbook runs to resolve their tools.
