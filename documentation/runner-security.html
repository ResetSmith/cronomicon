Runner security posture & blast radius (R7.6)

The credential-model record for the runner agent (cronomicon-runner), analogous to the key-custody record for the server's own SSH execution in execution-update.md EX.9. It states, in concrete terms, what an agent holds, what Cronomicon holds, what a compromise reaches, and how that trades against the local runner — the server running shell jobs itself. Where this guide says runner without qualification it means an agent.

One-line posture (credential model b, runners-update.md D1 — locked). The agent holds its own keys and inventory; for the keys it connects to its targets with, Cronomicon never decrypts or transmits private-key bytes. For an agent's runs the control plane holds nothing that reaches a target — it only tells the agent what to run and references where. The one deliberate exception is material a job binds (a Secret, or an SSH key reference), delivered only to an agent an operator has flagged for Secret injection (§2).

1 · What flows over the wire (and what never does)

A runner claims a run, then fetches a manifest (GET /api/v1/runs/{traceId}/manifest). The manifest carries (internal/runnerproto, ManifestResponse):

  • traceId, jobName, runType, executor
  • the resolved command: interp[] + body (interpreter argv + script/command)
  • env — the run's env snapshot (plain config values, runs.env_json), not secrets
  • targets: name, address, port, user, via (bastion), and authKeyEnvVar — the NAME of the key, never the key
  • inventoryMode, scope, timeoutSeconds, sensitiveLogging
  • inventory (ansible only) — the byte-exact Ansible inventory file the agent writes to a temp file for ansible-playbook -i, and limit (an --limit expression of host/group NAMES). The inventory is secret-free by invariant: secret-bearing vars (ansible_ssh_pass, ansible_become_pass, …) are rejected at INGEST (internal/inventory.ValidateSecrets, fail-closed) so a decrypted secret value can never reach this field. It is attached only for cronomicon-mode ansible runs; a local-mode runner is never shipped an inventory (the no-leak property — its host list never crosses the wire).
  • sshUser / sshKeyRef (ansible runs carrying a connect-as override) — the run's identity override as names only: a username and the derived CRONOMICON_KEY_<label> reference. The agent emits them as ansible connection extra-vars; the key's material travels only in the keys block, and the agent fails the run closed if it did not arrive.
  • ansibleOptions (ansible runs that set them) — the operator's per-run --check/--diff/--tags/--skip-tags/verbosity/--become/-e selection. Flags, NAMES and operator-typed literals only. Note the argv exposure: -e name=value pairs become process arguments on the runner host, readable by any local user via ps — a weaker position than the env channel, so extra-vars are documented as a non-channel for secret material.
  • checkout (checkout runs only) — the repo clone URL, a full commit SHA (never a ref), and the entry playbook / project root for a runner-side pinned project checkout. It carries no credential: the deploy token is runner-local (-checkout-token-file), and the SHA is verified against the runner's own -checkout-repos allowlist before anything is fetched. See §8 for the full checkout security model.

What never flows server → agent, unless the agent is flagged for Secret injection: private-key bytes, KEK-decrypted secret material, or any vault secret value (and never inside the inventory field — see above). The manifest's authKeyEnvVar is a reference; the agent resolves it locally (internal/agent/ssh.go loadSigner) to a key it already holds. The (a) model — the server minting/shipping short-lived key material via an Cronomicon CA — is shelved; nothing in this path implements it. This is the load-bearing property: for an agent that carries no Secret injection flag, a server-side compromise yields no key that reaches its targets, because the server never had one. The flag is the operator's explicit decision to make an exception for one agent: a run whose job binds Secrets, an SSH key reference or a connect-as credential is dispatched only to a flagged agent, and its manifest then carries the resolved values and key material for that run (the sections under §2).

A host record's stored SSH key credential is the local runner's, not an agent's. Cronomicon's typed, envelope-encrypted SSH keys (Env Vars → SSH Keys; a host's authCredentialId) are held on the server and used by the local runner, which dials from the control plane. To an agent the manifest carries the authKeyEnvVar NAME and the agent resolves it to a key it holds locally — the host's credential never crosses the wire. So a host an agent will connect to must reference its key by name (the picker's key-by-name option), not by credential. This matters more than it did: nothing on a job chooses its runner, so a shell job on a scope that an agent and the local runner both serve may be taken by either. Bind the scope to the runners that hold the right keys (runner-manage.html §4.8).

In inventory=local mode the manifest is even thinner — it carries only the scope name, not target topology, so the control plane never learns the host list of an isolated segment (runner-install.html §7).

2 · Key custody is DISTRIBUTED, per-runner

Each runner holds only the keys for its own segment, resolved by name in this order (loadSigner):

  1. an explicit -key-map entry (NAME=/path/to/key),
  2. an env var of that NAME holding a PEM, or
  3. a file named after the NAME in -key-dir.

Blast radius of an agent compromise is bounded to that agent's segment — and to one agency. Compromising runner-isolated-seg-a exposes only the keys that agent holds and the targets it can reach — not every target in the estate, and not the keys held by other agents. And because an agent serves exactly the agency that owns it (§11), the runs it is ever handed, and any secrets delivered with them, are that one agency's. This is the central contrast with the local runner.

Contrast with the local runner (EX.9)

The server can run shell jobs itself, as the local runner (called the in-app SSH executor before 2.3.0). It is off on a new installation; a global administrator turns it on under Settings → Local runner and lists the agencies it serves. While it is on, the server logs a loud warning that it holds SSH keys and opens outbound SSH.

EX.9 consciously accepted the centralized custody + broad outbound reach of the server running jobs itself as the right trade for the v1 reachable-target workload. An agent makes the opposite trade — it distributes custody and keeps the control plane key-free — which is exactly why it's the chosen path for ansible/ terraform (T-a, owns its own vault/inventory) and network-isolated targets (T-b, the agent lives where the app can't reach). The cost of distribution is operational: keys and known_hosts must be provisioned and rotated on each agent rather than in one place. An installation that wants the control plane to hold no key that reaches a target leaves the local runner off, or starts the server with CRONOMICON_LOCAL_RUNNER=forbid, which also locks the setting.

Which of the two takes a run is not chosen on the job. A queued run is taken by the first eligible runner that asks: one that serves the agency of the run's scope, is among the scope's bound runners if it has any, can run the run type, and may receive what the run carries (runner-manage.html §4.7). So a shell job on a scope that both an agent and the local runner serve may connect from either place, with either set of keys, run to run. Where that matters — and for custody it usually does — bind the scope to the runners that should serve it. One rule is fixed: the local runner never takes a run that binds an SSH key, because a bound key is delivered as a file on the machine that runs the job and only an agent does that.

How a runner authenticates, end to end (the three paths)

Cronomicon has three execution paths; it helps to see how each proves who it is to a target and which host it trusts. Only the two agent rows are model (b):

One key file serves both agent paths. A key provisioned once — a -key-map entry, or a file in -key-dir named after the authKeyEnvVar — serves bash/Go-SSH runs AND ansible: the agent bridges the NAME to that file's path and hands ansible --private-key <path> when a run's targets share one key, and/or fills the env var an inventory's ansible_ssh_private_key_file: "{{ lookup('env', NAME) }}" reads. You do not provision the same credential twice (a key file for bash + an env-var-holding-a-path for ansible). Each run's log names what authenticated it — cronomicon: auth: key "NAME" → <path> and cronomicon: auth: --private-key NAME → <path>. A run carrying a connect-as key override suppresses this auto-wire entirely (the log says so), because the two wire the same concept through different precedence tiers and only the override's tier reliably wins.

An env-held PEM is Go-SSH-only. A key held only as a PEM in the agent's environment (resolution step 2) can serve Go-SSH runs but cannot be handed to ansible — ansible needs a file path, and a PEM is bytes, so the bridge never materializes it. For a NAME ansible must also use, provision it as a -key-map entry or a -key-dir file (step 1 or 3); the installer's --generate-key NAME writes exactly such a file.

One trust store for both paths. ansible's OpenSSH verifies target host keys against the agent's own known_hosts — the agent injects ANSIBLE_SSH_COMMON_ARGS=-o UserKnownHostsFile=<store> -o StrictHostKeyChecking=yes — so the host-key review (§5) covers ansible runs too: the same approved host keys serve bash and ansible, with no ~/.ssh/known_hosts symlink workaround needed. A checkout project shipping its own ansible.cfg can still override this (presumed intentional). -no-auth-bridge opts out of both the key bridge and the known_hosts injection (estates that manage their own ansible SSH config); -ansible-ssh-common-args replaces the injected value for ProxyJump / cipher-restricted estates — it must stay fail-closed (never add StrictHostKeyChecking=no).

Prove the chain before a run. cronomicon-runner doctor --auth NAME [user@host] resolves NAME exactly as a run would and, given a target, dials it with the agent's own stack — reporting auth OK / host-key-unknown (points at Scan keys, §5) / permission-denied distinctly. The full doctor also lists resolvable key names and warns on a passphrase-protected or unreadable key; the expanded Runner detail shows those names as chips, so a missing credential is visible before the first failed run.

Non-root caveats. The runner unit runs with NoNewPrivileges (§7): that blocks privilege escalation on the runner host itself — an ansible become / local sudo executed on the runner is denied — but it does not affect become on a remote target (that is the target's own sudo, reached over SSH, unaffected by the runner's sandbox). Key auth also assumes the target accepts the runner's public key: a GSSAPI / Kerberos (AD) target still needs the runner's key in the login user's authorized_keys, or SSH falls through to a Kerberos method the runner isn't configured for.

Per-run connect-as credentials ride the delivery channel, under the same gates

An operator (or a job definition) may attach a stored SSH credential to a run as its connect-as identity — the target's key selection for that one run. When the local runner takes such a run the server connects with that key itself, and no key material is sent to another machine. When an agent takes it, this does not create a new material flow: the credential rides the existing key-delivery channel, the one a declared CRONOMICON_KEY_ binding uses — the key's agency checked against the run's at resolve, delivery audited to change_log, material written to a 0600 file off the run tree and wiped at run end, bytes redacted from ingested logs in lockstep. Each manifest target's authKeyEnvVar is rewritten to the delivered key's derived CRONOMICON_KEY_<label> reference, which the agent resolves to the delivered file ahead of its own key-map/key-dir.

Ansible runs. The same identity applies to ansible run types, over a different carriage but the same material path. Rewriting targets is not enough there: ansible-playbook opens its own connections and the agent never reads targets[].user. So the manifest carries two explicit fields — sshUser and sshKeyRef (the derived CRONOMICON_KEY_<label> reference, names only) — which the agent turns into connection extra-vars (-e ansible_user=…, -e ansible_ssh_private_key_file=<delivered path>). Extra-vars are ansible's highest-precedence source, so the override beats an inventory-authored identity on every host; the lower-precedence -u/--private-key flags would have lost to the inventory on exactly the hosts an admin had wired. Two fail-closed properties: the agent refuses the run if sshKeyRef names material that was not delivered (rather than silently connecting with the inventory's key), and it suppresses the --private-key auto-wire while an override is in force, so one run can never carry two keys through two precedence tiers. Material custody is the same as for the ssh family: the same delivery channel, the same agency check, audit, 0600 off-tree file, wipe-on-cleanup and lockstep redaction. As with the ssh-family case, the override decides who chooses the pairing, not what may be delivered. Terraform carries no identity at any layer.

What changed is who chooses the pairing — the operator at trigger time (gated by Manage Env Vars, the same permission as binding a key reference) or the job author — not what may be delivered: the same material was already reachable via a declared CRONOMICON_KEY_ binding under the same gates. Two enforcement points keep the posture honest: among agents, a credential-carrying run is claimable only by an allow_secret_injection agent (the claim fence covers the per-run credential exactly like a declared binding), and a local-inventory runner refuses the run (409) — its users and keys come from its own inventory, so it cannot honor the override, and refusing beats running as the wrong identity. A connect-as credential is not a key binding for the rule in §2 above: it does not keep a run off the local runner. A declared CRONOMICON_KEY_ binding, or a key reference added in the Run dialog, does.

3 · Run-ownership authorization (no cross-run access)

A valid runner token authenticates a runner, but the manifest and log endpoints additionally authorize by run ownership: a runner may only fetch the manifest for, and post logs to, runs it actually claimed (run.runner_id == caller). Otherwise the response is a deliberate 404 (not 403, so a non-owner can't even confirm the run exists). This matters even under model (b), because a manifest still exposes another run's env snapshot + target topology, and the log endpoint would otherwise allow cross-run log spoofing (any runner posting logs onto any run). Both GET …/manifest and POST …/log are gated; a regression test covers a non-owning runner being refused.

4 · Protocol-version handshake

The agent and server share a wire-protocol version (runnerproto.ProtocolVersion, currently 14; the comment above that constant documents the wire shape). The server enforces a floor, runnerproto.MinProtocolVersion, that tracks the current version: an agent that declares anything older — or declares nothing — is refused at POST /runners/register, at redeclare and on every poll with 426 protocol_too_old, a loud and actionable error rather than a silent mis-drive. The poll check is what makes a server upgrade safe: an agent registers once and resumes its identity afterwards, so without it a runner enrolled before the upgrade would keep polling at its old protocol. Server and agent ship from one repository and the Copy upgrade command on the Runners page moves a fleet with its server, so keep them in lock-step across upgrades; the handshake turns drift into an explicit, diagnosable failure wherever the agent talks to the server.

Protocol 14 (2.2.0) makes host-key trust two-way. Until 13 the server could only add to a runner's known_hosts. 14 adds two poll control ops: untrust-hosts, which carries the lines the agent removes (a replaced or operator-removed key), and known-hosts-report, which asks the agent to upload what its file holds. An agent that silently dropped either would leave a replaced key trusted and every delivery unconfirmed, which is why this is a version bump and not an additive field: upgrading the server to 2.2.0 refuses every protocol-13 runner on its next poll until that runner is upgraded too (runner-manage.html §3). The refused runner keeps its row, its identity and its placement; it shows as alive and refused, not reaped. 2.3.0 leaves the protocol at 14: what it changes — an owner for every runner, the local runner, one claim rule for every run — is all on the server, and an agent sends nothing new.

No per-feature back-compat gates. The server carries no family of per-feature agent_too_old refusals behind the floor. Every manifest field and control op (inventory, checkout, secrets, connect-as identity, ansible options, the become-password file, resync, host-key scans, host-key removal and the known_hosts report, file-watch distribution) would be silently dropped by an agent that did not understand it, and that agent would run the wrong thing; with the floor at the current version that situation cannot arise, because a runner below the floor cannot register and is refused on every poll, so it is never handed work. Everything past that check assumes the current wire shape. The security posture of the individual ops is unchanged: the re-register op carries no configuration (the agent re-reads its own local config and re-declares it with its existing crn_run_* key, so a compromised server or operator session cannot use resync to grant a runner capabilities, and no registration token is involved); the drift digest is a hash of what the agent already declares, never a channel for new config, and its delivery is flap-guarded.

5 · Host-key verification expectations (on the agent)

Host-key verification for the target hop is the agent's responsibility and is strict by design (internal/agent/ssh.go hostKeyCallback):

  • Point -known-hosts / CRONOMICON_RUNNER_KNOWN_HOSTS at an OpenSSH known_hosts file. The presented target key must be in it. Unset ⇒ the agent uses a default path (beside its identity file) and creates it empty, so a fresh runner starts with an empty trust store — every unknown host is refused until approved (below).
  • There is no fall-open. An unknown or changed target key is a hard connect failure, surfaced per-host — there is no InsecureIgnoreHostKey path on the target hop.
  • This one store serves ansible too. Local-toolchain (ansible) runs verify against the same known_hosts — the agent points ansible's OpenSSH at it — so the review below applies to ansible as well as Go-SSH runs (see §2, "How a runner authenticates"). Disable with -no-auth-bridge.

Scan, review, approve. Nothing is trusted on first connect, by an agent or by the server. Instead of assembling a known_hosts by hand, you can trust a target's key at the moment it's actually known: an SSH run that fails host verification surfaces a host_key_unverified reason naming the host; in the Runners view, Scan keys opens the Host keys dialog, which takes keys from four sources — Scan a scope or Scan hosts (delivered as a keyscan control op; the agent captures each presented key from its own vantage, without authenticating, and uploads it), Paste keys (lines the operator already holds) and Copy from a runner (the keys another runner trusts). Every source ends on one review screen that shows the full SHA256 fingerprint of every key and classifies it as New, Matches server (equal to the key approved for the local runner — the server — for that host, same key type and port), Already trusted, Changed, or Cannot accept. You compare each fingerprint out-of-band against the host itself, then press Trust N keys on <runner> — the runner's poll delivers a trust-hosts op and the agent appends the lines to its known_hosts. Retry the run; it now verifies. The operator steps are in runner-manage.html §4.6.

The server does not take anyone's word for a key. Whatever arrives — a runner's upload or an operator's paste — is parsed on the server, the fingerprint is computed from the key rather than read from the request, and the line a runner receives is rendered by the server for one validated host. Nothing an agent or an operator typed reaches a runner's file verbatim, so a line cannot smuggle a second trusted host in. A paste is refused if it carries a wildcard or negated host, a @cert-authority or @revoked marker, or a host the runner's verifier could not load — one unreadable host makes a runner's whole file unloadable and fails every run on it — and a paste is accepted whole or not at all. The agent keeps its own guard as defence in depth: it never writes a multi-line entry.

An approval is bound to what was reviewed. A commit names the rows that were ticked by host, key type, fingerprint and the status shown. A key that changed at the source since the screen was drawn, or one that would replace a key the runner already trusts without having been ticked as Changed, refuses the whole commit (409 review_stale). The review screen's select-all never ticks a changed key, and a key that arrives from a running scan after the list opened is left unticked.

The ledger is the record. Every decision is a row in an append-only host-key ledger: the decision (approved, rejected, removed), the source (scan, pasted, carried), the runner by id and name (the record outlives the runner), the scope and host, the previous fingerprint when one was replaced, the actor, and a batch id. A key is in force while its approval has not been superseded. One approve/reject action is one transaction, one batch and one Host Keys row in the Change Log that names the runner and the scope and expands into the individual keys; the audit export has a Runner Host Keys event type with one row per key. This replaces the pre-2.2.0 record, which was a change-log row with a host and a fingerprint but no runner, over a pending row that the next scan overwrote.

Trust can now be taken away. Approving a Changed key supersedes the earlier approval for the same host and key type, and the runner is sent an untrust-hosts op for the old line together with the new one — a rotated host key no longer leaves its predecessor trusted. Remove on the runner's Trusted host keys panel does the same with no replacement. The agent deletes only a line that names exactly that one host with exactly that key and no marker; a line naming several hosts is left alone, because removing it would untrust hosts nobody asked about. The file is replaced by rename, so a run dialling at that moment reads the old file or the new one, never a partial one.

Delivery is confirmed by the runner's own report, not assumed. A key used to be marked delivered when it was sent. Since protocol 14 the agent reports its known_hosts when it starts, after every change the server makes, after a re-registration and when an operator asks: per line, the host patterns, a hashed flag, any marker, the key type and the fingerprint — never the file itself, and never a hostname hash. The report is believed over the ledger's own stamps: an approved key the file does not hold is shown as Not in the file and is queued again when re-approved or on Send again; a retired key still in the file is queued for removal again, at most hourly; and scope coverage does not count an approved key that the last complete report lacks. A report carries at most 5,000 entries and says when it was truncated.

What Cronomicon approved and what the file holds are shown separately. The panel lists Approved in Cronomicon and, apart from it, Present in the runner's known_hosts file, where each line is marked Approved here, Not approved here, Revoked or Certificate authority. A line that is not approved here — a pre-seeded file, an edit on the host — is trusted by the runner all the same; the panel makes it visible, it does not govern it. Cronomicon edits only the entries it manages.

Retention. A ledger row is never pruned while its key is in force, whatever the setting. Rejected, removed and replaced rows age out after the Host Key History window in Settings → Audit & Compliance (365 days by default). Authority. Scanning, providing keys, approving, removing and reading a runner's host-key record all need configureApp on the agency that owns the runner (a global administrator, for a runner that is Global's), because the record names the hosts of the scopes that runner serves; a scope scan additionally needs the scope readable and the runner to serve the scope's agency. Copying keys from one runner to another needs that authority over both.

One narrow exception: an agency a runner serves and does not own. The local runner, and an agent left serving several agencies by a pre-2.3.0 placement (§11), are Global's, and without an exception a department would wait on a global administrator for every new host. So an administrator of an agency such a runner serves may queue a scan of their own agency's scopes with it and see what that scan found — nothing else: not typed hosts, not a paste, not a copy, not a removal, not the record. On an agent they may also approve a first key, for a host the runner holds no key for of any type. They may never replace one, nor approve a key that contradicts the server's (403 owner_required): the limit on a guest is the scope a key was scanned for, but what an approval writes is the runner's trust in that address, whoever else uses it — a host can sit in two agencies' scopes, and a bastion serves many. On the local runner a guest approves nothing at all, for the same reason at full strength: the server's trust in an address is one fact for every agency whose runs and secrets it handles, so only a global administrator decides it.

The server is held to the same rule. Until 2.3.0 the server kept a key on each host record and captured it the first time it connected. It no longer captures anything. The local runner connects only to a host — and through a bastion — whose key is approved and in force on its own record in this ledger; anything else fails that host with host_key_unverified, and a different key from the approved one with host key mismatch … possible MITM. That holds for a run and for Test connection, which now reports unverified and trusts nothing. An approval for the local runner is in force at once, since there is no file to deliver it to. The keys the server had captured before the upgrade were carried into the ledger as approved, with the source carried; where two records for one address disagreed, one is trusted and a notice names the other. One limit follows from keying trust by address: the local runner holds one key per address and key type, so two machines that share an address behind different bastions cannot both be trusted by it.

Approving a key you have not verified out-of-band trusts whatever answered. The scan tells you what key the host presented to the runner right now — it cannot tell you the host wasn't already compromised or MITM'd. A Matches server status says the runner and the server hold the same key, which is corroboration from a second vantage, not proof — and it is shown only when the server's key was approved for no particular scope, or for a scope of an agency the reviewing runner itself serves, so that a decision made for one agency's hosts is never the second opinion another agency reads. The review screen shows the full SHA256 so you can compare it against the fingerprint the host's admin publishes (or ssh-keygen -lf on the host itself). This is strictly better than pasting blind ssh-keyscan output — it's recorded and asks at the right moment — but the out-of-band comparison is what makes it trustworthy. The same holds for Copy from a runner: two runners sit in different places on the network, so the same address is not guaranteed to be the same machine. Pre-seeding a curated known_hosts (--known-hosts) remains available and skips the scan for hosts you already trust.

6 · Bastion / ProxyJump trust note

When a target's via is set, the agent makes a ProxyJump-style hop: it dials the bastion, then tunnels an SSH connection to the target through it (internal/agent/ssh.go dial). Trust implications:

  • The agent must be able to reach the bastion, and the bastion the target — the app is not in this path at all for an agent's runs. (When the local runner takes a run, the server makes the same two hops itself and verifies the bastion under the address its record is dialled at, against the keys approved for the local runner.)
  • The agent authenticates both hops with its own key (model b) and applies the same strict host-key verification to the bastion as to the target — both must appear in known_hosts. A compromised or spoofed bastion is therefore caught by host-key verification, not silently trusted.
  • A target behind a bastion cannot be scanned. The key scan dials directly and does not tunnel, so a scope scan lists such a host as not scanned, with the name its line must start with, and its key is supplied with Paste keys (§5). The bastion itself is dialled directly, so it is scanned. Scope coverage counts a host behind a bastion as trusted only when the runner trusts the bastion's key as well as the target's.
  • Because the bastion sits between the agent and the target, it remains a privileged pivot inside the segment: treat the bastion host with the same custody discipline as the runner itself.

7 · Operational hardening (defense in depth)

The credential model is the primary control; these reduce the impact of a host compromise:

  • Run as non-root, hardened. The cronomicon-runner.service unit runs a dedicated user with NoNewPrivileges, ProtectSystem=strict, a single writable StateDirectory, and a restricted syscall/address-family set. It sets no resource limit unless you give it one, and an agent that is not root cannot cap its own runs (§8): on a machine that hosts several agents, give each unit a memory, CPU and task limit (runner-install.sh --memory-max, --cpu-quota, --tasks-max, or systemctl set-property), or one agency's run can take the machine from the others. The container images run as a non-root user with no shell (slim) / a single-purpose userland (fat).
  • Protect the identity file and keys. The identity file (crn_run_* bearer) is written 0600; keep it and the key directory on storage only the runner user can read. Possession of the identity key lets a host act as that runner (claim its runs, post its logs) — but still cannot retrieve another runner's keys or the control plane's secrets.
  • Rotate per-runner. To retire a compromised runner: Deregister it on the Runners view, delete its identity file, and rotate the SSH keys it held. Because custody is distributed, this is a segment-local rotation, not an estate-wide one.
  • Least-capability runners. Declare only the capabilities a runner needs. Capability routing then guarantees it never claims (and never sees the manifest for) run-types outside that set.
  • Bind the scopes that matter. An agent takes any run of its agency that it is eligible for. Binding a scope to the runners that reach its hosts (runner-manage.html §4.8) keeps that scope's runs — and the secrets they carry — off every other runner that serves the agency, the server included.

8 · Ansible checkout: security model, dependencies & Vault

Runners started with -allow-checkout execute playbook projects checked out at a server-pinned commit SHA — a materially larger power than the body-only path, bounded by four controls plus the sandbox. The threat model is single-tenant-trusted: playbook authors are internal operators gated by GitLab MR review, so the realistic threats are honest mistakes and poisoned third-party dependencies, not a hostile author. (If runners ever execute mutually-untrusted teams' code, that model must be revisited before enabling checkout for them.)

The four controls that bound checkout:

  • Opt-in + repo allowlist. Checkout requires BOTH a job-side declaration (a project wrapper) AND the runner's -allow-checkout flag; the runner also refuses any repo outside its -checkout-repos allowlist. A compromised server cannot point a runner at an arbitrary repo, and an un-flagged runner is unaffected by the feature entirely.
  • SHA verification. The manifest carries a full commit SHA, never a ref. The agent verifies the commit exists before archiving and runs exactly that tree, so a repo compromise cannot swap the tree under a pinned run. The SHA is pinned at enqueue (a mid-run re-sync can't retarget an in-flight run) and logged as provenance.
  • Read-only, per-runner deploy credential. The runner fetches with its own read_repository-scoped GitLab deploy token (-checkout-token-file) — never shipped by the server, never written into the persisted mirror config. Worst-case leak is read access to one repo from one runner, not GitLab write or account access; revocation is per-runner. runner-install.sh places this file for you — --checkout-token-file <path> installs a staged file, or --checkout-token - reads it from a hidden stdin prompt — always at 0640 root:cronomicon-runner. The installer refuses a token passed as a flag value (it would leak via ps / shell history).
  • Tree secret-scan. The INI-only inventory guard never sees playbook trees, so a vars/main.yml or .j2 could smuggle a plaintext secret the redactor will never know. cronomicon validate (error in CI) and git sync (advisory warning) scan a project's YAML/INI/template files for inline secret-bearing vars outside vault-encrypted files — matching both key=value and key: value forms. Vault-encrypted ($ANSIBLE_VAULT) files and lookup('env',…) indirection are exempt.

Tier 2 sandbox (host-native). Each local-toolchain run is wrapped in a per-run systemd-run --scope cgroup for resource caps; the filesystem/namespace/syscall hardening (ProtectSystem=strict, PrivateTmp, NoNewPrivileges, the syscall filter) is inherited by the child from this runner's own systemd unit. Sandbox availability is detected, never assumed: where the agent cannot create a scope, runs execute unsandboxed and are reported as such (a loud startup warning and a per-run provenance line for checkout runs). A sandbox-capable runner advertises a sandboxed capability token, so a job may requires: [sandboxed] to never land on an unsandboxed host. An agent set up by the installer is not sandbox-capable. systemd grants a new scope only to root, the unit runs the agent as its own user, and Cronomicon ships no polkit rule to change that: the permission involved is the one to manage units, far more than an agent should hold. So on an ordinary install every local-toolchain run inherits the hardening above and has no resource cap of its own; the caps are stored and never applied, and a job that requires sandboxed waits. The bound that does hold is a limit on the agent's unit, which covers the agent and all its runs together. Egress control (an IPAddressAllow allowlist on the runner unit) ships commented opt-in in cronomicon-runner.service.

Supply-chain: two controls and one accepted risk.

  • Pinning is the supply-chain posture. The galaxy source defaults to the public galaxy.ansible.com (override with -galaxy-server for a private mirror/hub). Because the source can be open, reproducibility rests on pinning — every requirements.yml collection needs an exact version: and every git role a full commit SHA. cronomicon validate fails CI on an unpinned entry; sync warns. A collection already present at the exact pinned version in the runner's provisioned base is not re-downloaded (so a pre-provisioned runner runs offline); an unsatisfied pin whose download fails fails the run loudly — there is deliberately no fallback to a differently-versioned local copy.
  • Provenance is logged. Each checkout run emits the verified SHA, the ansible-core version, and every dependency install line — buying back the auditability that run-time installs cost.
  • Vault: decrypted values bypass redaction — use no_log. A job opts into Ansible Vault with requires: [vault]; the agent then passes --vault-password-file from its OWN runner-local config (the password never travels — configure it with -vault-password-file (installed by runner-install.sh via --vault-pass-file <path> or a hidden --vault-pass - prompt, at 0640 root:cronomicon-runner; never as a flag value), and register that same password as an Cronomicon stored secret so the log redactor masks it). The value-based redactor can only mask values Cronomicon knows; a value your playbook decrypts from vault at run time is not one of them. Any task that could print a vault-decrypted secret MUST set no_log: true — that is the only masking for decrypted vault values. Prefer env-var indirection (lookup('env','NAME')) over vault where you can: it is the only secret path the redactor fully covers.

9 · Referencing Cronomicon values in scripts & inventories

Cronomicon resolves a small, closed set of reserved CRONOMICON_* prefixes into values at run time. Any CRONOMICON_* name that starts with one of these four prefixes is a reference the app injects; every other CRONOMICON_* name is server/runner configuration and is never exposed to a run. An operator reading a script or inventory can tell the two apart at a glance.

PrefixEnv Vars sectionResolves to
CRONOMICON_VAR_*Variablesa plaintext value (log-safe)
CRONOMICON_SECRET_*Secrets (stored or Vault-backed)a sensitive value (always redacted in logs)
CRONOMICON_KEY_*SSH Keysa file path to key material on the agent's host — not the key bytes. Delivered by an agent only: the local runner never takes a run that binds one
CRONOMICON_RUN_*dispatcher (fixed set)read-only run context (reserved)

Derived-reference rule. Rows keep their bare names (e.g. a Secrets row NWD_BECOME_PASS, an SSH Keys row ansible_rh8_key); you form the reference by prefixing the section — reference = CRONOMICON_<SECTION>_<row name, verbatim>. Resolution strips the known prefix verbatim (case-preserved) to find the row or file. So CRONOMICON_SECRET_NWD_BECOME_PASS → the revealed value of Secrets row NWD_BECOME_PASS, and CRONOMICON_KEY_ansible_rh8_key → the path to key ansible_rh8_key. Nothing in the store or on the host is renamed.

Value vs. path. CRONOMICON_KEY_* resolves to a filesystem path — pass it where a tool expects a key file (ssh -i "$CRONOMICON_KEY_ansible_rh8_key"). The other three resolve to values — never write a value into a file the run leaves behind.

Secret hygiene in a run. An injected CRONOMICON_SECRET_* / CRONOMICON_VAR_* value is only as safe as the script handling it:

  • Quote every expansion — "$CRONOMICON_SECRET_X", never bare $CRONOMICON_SECRET_X — so a value with spaces or globs is not resplit.
  • Never echo a secret and never pass it on the command line (--pass=$CRONOMICON_SECRET_X) — argv is world-visible via ps. Prefer stdin or an env var the child reads directly.
  • Turn off tracing around secrets — set -x prints every expanded value; disable it (set +x) before touching one, or never enable it in a script that handles secrets.
  • Fail fast if a reference was not injected — guard with the POSIX idiom
    : "${CRONOMICON_SECRET_X:?not injected}"
    so the run aborts loudly instead of proceeding with an empty credential.

The value-based log redactor masks values Cronomicon knows, but that is a backstop — the controls above keep a secret from leaking through argv, a trace, or a file in the first place.

10 · Residual risks / notes

  • Distributed custody is more surface, less depth. Model (b) trades one high-value custodian (the app, EX.9) for many lower-value ones (the agents). The aggregate key material is larger and lives in more places; the win is that no single compromise is estate-wide. Provisioning/rotation discipline per agent is the operational cost you accept for the bounded blast radius. An installation that also turns the local runner on has both kinds of custodian, and the server's reach is every agency on the local runner's serve list.
  • A runner is trusted within its segment and its agency. Within its own segment an agent has the reach its keys grant, and it is handed every eligible run of the agency that owns it. Scope each agent's keys to the minimum (runner-install.html §8) so "that runner's segment" stays small, and bind scopes where only some of an agency's runners should see their runs.
  • The control plane is not a key oracle. This is the property to preserve in any future change: nothing should make the manifest or poll path carry key bytes or decrypted secrets to an agent that has not been flagged for Secret injection. If a central-key-custody mandate ever appears, that is the shelved (a) model and a separate, conscious decision — not a quiet edit to this path.
  • A legacy placement is a shared agent that has not been settled yet. It serves several agencies with one set of keys and one known_hosts, which is what the one-agency rule exists to end. It is tolerated so that an upgrade stops nothing, not endorsed: settle it (§11).

11 · Ownership: who an agent serves, and who may manage it

Two agents on one machine are separated by their OS users, and by nothing else. An agent installed with --instance <name> (runner-install.html §3) runs as its own user and group, cronomicon-runner-<name>, with its own state and config directories (0750) and its own unit. That is what keeps one agency's keys, deploy token, vault password, Git mirrors and run directories from the other's jobs: every run on an agent executes as that agent's user, and nothing inside an agent separates one run from another. The installer has no option to share a user or a group, and you should not arrange one by hand — the config files are readable by the group, and /dev/shm, where key material for a run is written, is one directory for the machine, kept apart only by the owning user. What the two agents do share: the binary (root-owned, so neither can change it), the kernel, the machine's network unless a unit drop-in narrows it with IPAddressDeny/IPAddressAllow, and the process list — the units do not set ProtectProc=, because not every supported distribution's systemd has it, so one agent's user can see that another's processes exist (what the server delivers as a secret travels by environment, file or stdin, never on a command line; values an operator types into a run as Ansible extra-vars are arguments, and are visible there). Root on the machine is root over every agent on it. Where two agencies must not share a kernel, give each its own machine or container.

Every runner has an owner agency. The owner decides two things at once: whose administrators may manage the runner, and — for an agent — whose runs it takes.

  • The owner is the operator's grant, held on the server. A registration token is minted for an agency, and the agent it enrols is owned by that agency. The agent sends nothing about it: there is no flag, env var or request field by which an agent can name, widen or change its agency. A token whose agency has since been deleted enrols nothing; the agent is not placed in Global instead. The environment bootstrap token names no agency and enrols Global agents.
  • Minting a token is granting an agency a runner, so it needs configureApp on that agency. An agency's administrators enrol their own agents; a global administrator may enrol one for any agency, or for Global. The token list shows a caller only the tokens of agencies they administer.
  • An agent serves exactly its owner. There are no shared agents and no pool of unassigned ones: what used to be "no agency" is the Global agency, a Global agent is a global administrator's, and it takes Global's runs only. An agent's owner does not change, with one exception below; to move a machine, deregister it and enrol it again.
  • Every write on a runner is its owner's: settings, tags, the Secret injection flag, drain, resync, deregister, and its host keys (§5, with the one exception stated there). A Global runner is a global administrator's.
  • Binding a scope is judged on the scope. It needs configureApp on the scope's agency and a runner that already serves that agency — not authority over the runner. A binding only narrows which of the runners already serving an agency a scope uses; it can never bring in a runner from outside it.
  • A runner's name carries no authority. The name is the agent's own word and is not unique. Its API key is tied to its id. When a host re-enrols, the offer to restore its previous placement is looked up by name, which is safe because of what a restore can reach: it re-points scope bindings on scopes of the accepting runner's own agency — which that agency's administrator could bind by hand — and never adds anything to what the runner serves. Enrolling an agent under another agency's runner name gets it nothing of that agency's.

Legacy placements. An agent that was in several agencies when the server was upgraded to 2.3.0 keeps serving them, so that the upgrade stops nothing. It is Global's, a notice lists it, and it can be narrowed and never widened; once it serves one agency it can be handed to that agency, the only owner change there is. runner-manage.html §4.9 gives the order for replacing one with an agent per agency without closing a bound scope.

The local runner. The server itself is a runner too: one row, Global's, never deregistered or reaped, and the one runner with a serve list. A global administrator decides whether it runs at all and which agencies it serves (Settings → Local runner; CRONOMICON_LOCAL_RUNNER=forbid on the host overrides the setting). For every agency on that list the server opens SSH to the targets with keys it holds, and resolves that agency's bound secrets in its own process — the centralized trade of §2, now stated per agency. It runs only the shell types, never a run that binds an SSH key, and only a global administrator decides which host keys it trusts (§5). Its configuration and internals are in the Administrator Manual §4.
